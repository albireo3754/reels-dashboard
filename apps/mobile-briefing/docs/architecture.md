# Mobile briefing and local object relay

The deployed application is an access-controlled Sites app. D1 stores the latest completed metadata snapshot. Original media stays in its existing local/iCloud Drive location. A local macOS service uses outbound HTTPS to sync metadata and fulfil bounded object reads; there is no inbound public port on the Mac.

## Data model

`sources` identifies the Mac and its heartbeat/current snapshot. `sync_runs` records each staged metadata ingestion. `contents` holds production state, date basis and next action. `assets` holds opaque object references, roles, file names, sizes and availability. `media_requests` holds short-lived byte-range requests. A new generation becomes visible only after all rows are written. Two completed generations are retained.

This is a relational design intended to remain understandable in PostgreSQL terms: primary keys, explicit source/run relationships, indexed content lookups, typed columns and atomic pointer publication. The deployed engine is **Cloudflare D1 (SQLite), not PostgreSQL**. A future PostgreSQL deployment would map run IDs to UUID, timestamps to timestamptz, availability flags to boolean and move the parameter binding/transaction layer behind its driver. No live PostgreSQL instance or untested migration adapter is claimed.

## Metadata boundary

The user requested a complete private mobile briefing. All registered production entries are projected regardless of their public sharing flags; the desktop sharing flags are not changed. Source paths, Photos asset IDs, private notes and credentials are omitted. File names and user-authored progress titles are visible only to the Site’s allowed viewers. Captured, selected, editing, review and published are distinct states; a local completed file is not evidence of publication.

## Object SDK and relay

The local `packages/icloud-object-sdk` provides HeadObject/GetObject/ListObjects-shaped methods, opaque registered keys, ETags and bounded reads. This is not an AWS S3/SigV4-compatible HTTP server. Sites native private HTTP binding support exists, but no tunnel registration tool was available in this environment; no tunnel ID was invented.

The deployed transport works as follows:

1. An authenticated mobile request selects a server-known asset ID.
2. The Site queues a byte range in D1. Browser clients cannot choose filesystem paths.
3. The outbound Mac service reads the approved object and sends at most 2 MiB per chunk.
4. R2 holds that chunk until the response consumes it; the read response supports HEAD, Range, 206, 416 and ETag. HTML/documents are attachment downloads rather than executable same-origin pages.
5. Completed chunks are deleted after consumption. Expired requests/chunks are cleaned when the bridge next polls. If the bridge is offline, residual chunks remain private until cleanup resumes; no lifecycle expiry claim is made.

Mac sleep/offline affects source-file access, not the last saved briefing. Metadata is refreshed every minute and heartbeat every ten seconds while the service runs. iCloud must make the selected source readable on the Mac. This does not mount iCloud as a cloud-hosted bucket or promise access while the Mac is off.

### Low-resolution video previews

Set `MEDIA_PREVIEWS_ENABLED=true` to enable this path for signed-in viewers in the existing Sites audience. `MEDIA_READS_ENABLED` independently controls original-file access. Content details and matching video pins in the capture map show **미리보기 재생** for registered video files. The player shows preparation, connectivity and errors, with a retry action. It uses the latest completed snapshot to resolve the asset ID and waits for a recent Mac heartbeat.

- `POST /api/previews/{assetId}` prepares a derivative or retries a failed preparation. `GET` on the same path reports `idle`, `offline`, `pending`, `error` or `ready`. D1 deduplicates preparations by source object key, source ETag and preset `h264-540-v1`. Pending jobs expire after 150 seconds. Ready and error results have a 15-minute lifetime. A new source revision uses a new preparation. Closing a viewer stops its polling and leaves shared preparation running.
- The authenticated bridge heartbeat advertises `previewsEnabled` and `mediaEnabled`. `GET /api/bridge/preview-jobs` supplies bounded `prepare` and `range` jobs with UTC ISO `expires_at`. A result PUT on `/api/bridge/preview-jobs/{id}` accepts JSON `{bytes,etag}` for preparation or an exact octet stream for a range. An empty body with `X-Reels-Source-Error` reports `SOURCE_CHANGED`, `SOURCE_UNAVAILABLE`, `NOT_LOCAL`, `PREVIEW_FAILED` or `PREVIEW_TIMEOUT`. Stale, expired and duplicate results return 409.
- `GET/HEAD /api/previews/{assetId}/media` uses the derivative's size and ETag. The player pins the preparation ID with `?v=` so that later seeks keep the same derivative. The endpoint handles 206 and 416 and sends private, no-store responses. GET returns after the first chunk of at most 256 KiB and streams subsequent chunks of at most 2 MiB. HEAD creates no relay jobs. Reported range source failures invalidate the corresponding preparation so a retry asks the Mac to prepare it again.
- `preview_ranges` and the R2 `preview-relay/` prefix isolate transfers. The Worker removes consumed data, waits up to 16 seconds for each range, and gives each range job a 30-second lease. Bridge heartbeat cleans expired rows and objects in bounded batches even when preview access is disabled. An interrupted upload has a one-minute cleanup grace period. Cleanup of residual data resumes when the bridge reconnects.

Run `npm run build && npm run test:preview` with FFmpeg (`libx264`) and Playwright Chromium installed. The test starts loopback Workers with in-memory D1 and R2, applies all Drizzle migrations, generates a synthetic MP4, and uses fixture authentication in the test client. A phone-sized headless run checks the player. Real-device and hosted sign-in checks require separate verification.

## Authentication and deployment

Sites owns browser sign-in and configured audience access. Service requests require both Sites service access and the application bridge header. The runtime secret is configured through Sites; the corresponding local credential is stored in macOS Keychain. The LaunchAgent contains only paths and the Keychain account name. Secrets never enter source or browser bundles.

The Site and desktop share one source repository. Each release projects the Site and shared briefing package into the private Sites repository. Personal snapshots are sent through the private update endpoint, not committed as seed data or schema migrations. The app remains independent of the Obsidian runtime.

## Capture route synchronization — 2026-10-31

## Paseo request copy — 2026-11-20

The after-work pick card has one `Paseo에 붙여 넣을 요청 복사` button (since 2026-11-21 inside the collapsed "Paseo로 직접 이어가기"; see Mobile instructions). It copies a fixed request that the user pastes into their own Paseo session; the Site does not send, run, approve or resolve anything and makes no server write. Payload, D1 schema, Worker routes, authentication and the desktop bridge are unchanged, so this ships without a schema-first deployment.

The text comes from the pure `buildPaseoRequest` in `lib/paseo-request.mts`: a constant lead sentence (`reels autopilot inbox`로 현재 상태를 읽고 판단할 한 가지와 근거를 보여 달라는 요청), `대상: <today.target>` and `화면 기준 시각: <KST>`. The time is the completed snapshot time shown as 마지막 동기화 (`syncedAt`, falling back to `monitor.generatedAt`). Free card text — title, why, decision, doneWhen, outcome — is never included, and targets with specific character or format risks are rejected. The target must pass the existing contract (`project:<id>` or an http(s) URL, at most 2,048 characters) and additionally contain no character in the Unicode whitespace/separator (`\s`, `Z`), control (`Cc`), format (`Cf`, which includes zero-width, bidi, BOM, U+E0000–E007F tags and U+1D173–1D17A), default-ignorable, surrogate (so lone surrogates are rejected), private-use or unassigned classes. Hangul and other visible letters, encoded URLs and emoji remain valid. The strict monitor schema itself still accepts these characters, including a newline inside `project:` targets. This narrows, but does not remove, prompt-injection risk: the target is still a synchronized identifier and the receiving agent must treat it as data, not as an instruction. A missing or rejected target disables the button and states why; the screen time is always shown.

Each click first clears the previous result and shows a pending state; the button is disabled until the write settles, so duplicate clicks do not start another write. The success message appears only after `navigator.clipboard.writeText` resolves. If the clipboard is unavailable or denied, no success is shown and the same text appears as selectable text, following the publishing-copy pattern. Offline and signed-out behaviour is unchanged: data stays as last loaded while offline, and a 401/403 clears the briefing, including this control.

## Mobile instructions — 2026-11-21

The user decided (D13) that the Site should accept work instructions directly. Anyone with Site access writes a free-text instruction on the phone; the Mac bridge claims it, runs a visible agent and reports status and a short result back. Values follow decisions D14–D21.

**Data.** Migration `0005_clean_shooting_star.sql` adds `instructions` (text, optional verified target, optional end level, status, timestamps, session name, summary, question, error code; unique `(owner_id, idempotency_key)`; `owner_id` is the signed-in requester), `instruction_events` (one audit row per creation, claim, status change, cancel and expiry; fixed note codes only, never text or paths) and three nullable `sources` columns for bridge readiness. Instruction text lives only in D1. API responses never include `owner_id` or `idempotency_key`, and server logs only carry error names.

**Who may instruct (user decision, 2026-11-21).** Site access is the permission. Any request the Sites front door signed in (`oai-authenticated-user-id` present) may create, list and cancel instructions; there is no separate owner allowlist. A missing header gets `401`. Who can reach the Site is governed only by the Site's access policy, so adding a viewer to the Site also lets that person run agents on the Mac through this queue. The queue is shared: everyone sees all items (latest 30) and can cancel any queued one. The signed-in id is stored only for per-person rate limits and idempotency and is never returned. Briefing and media reads keep the previous rule (bridge key or a signed-in user). `GET /api/whoami` returns only `{header, canInstruct}` booleans. An earlier draft of this feature (D18) compared ids against an `OWNER_USER_IDS` allowlist with a staged rollout; the user removed that requirement.

**Site user API.** `GET /api/instructions` (latest 30 of the shared queue, expiry applied on read, Mac online/readiness, switch state), `POST /api/instructions` (`{text, target?, endLevel?, idempotencyKey}`) and `POST /api/instructions/:id/cancel` (queued only). Writes require `Sec-Fetch-Site: same-origin` when present, an `Origin` equal to the request origin when present, and at least one of them (`403 CROSS_SITE`); JSON only (415); body ≤ 24 KiB (413); text 1–4,000 code points and ≤ 16 KiB UTF-8, no control characters except newline/tab, no lone surrogates. Targets must pass `validPaseoTarget` and exist in the latest snapshot (a content id or today's target). The idempotency lookup runs before the limits: the same key and payload returns the same row (200), a different payload is `409`, and an expired or cancelled row is returned rather than recreated. Limits: 3 per minute and 20 per 24 hours per signed-in user (`429 RATE_LIMITED`), 5 unexpired queued in total, since one Mac runs everything (`429 QUEUE_FULL`), checked inside the insert statement. Queued rows expire after 24 hours.

**Bridge API** (`x-reels-bridge-key` only; user headers get 401). `POST /api/bridge/instructions/claim` `{capacity:0..2}` returns nothing when `INSTRUCTIONS_ENABLED` is not `true`. Otherwise expiry, the active check (claimed + running < `INSTRUCTIONS_MAX_ACTIVE`, default 1; `needs_user` does not count), selection of the oldest unexpired queued row, the conditional transition and the audit row run in one D1 batch, so concurrent claims and a cancel/claim race have a single winner. A claimed row that has not become `running` within `INSTRUCTIONS_CLAIM_TIMEOUT_MINUTES` (default 10) — for example because the claim response never reached the bridge — is turned into `failed` with `error_code=CLAIM_LOST` and one server event, in the same housekeeping step as expiry (every read, create, cancel and claim batch). It is never re-queued, so an instruction runs at most once, and a late `running` report gets 409; the bridge itself cannot send `CLAIM_LOST`. `POST /api/bridge/instructions/:id/status` allows only claimed→running|failed and running→needs_user|done|failed. Reporting the status the row already has (a retried upload) is an idempotent 200 with `unchanged: true` and the current item; nothing is written (no event, timestamps and fields unchanged). Other transitions get 409 with only `{error, status, error_code}`, so the bridge can tell "already there" from, say, `failed`/`CLAIM_LOST`. `running` needs a session name (letters, digits, space and `._:#()[]-`, ≤120, no path/token shapes); `needs_user` needs a question (≤500); summaries are ≤2,000 code points and ≤10 lines; error codes come from a fixed set. Lines with control/format/invisible characters, local paths, file URIs or credential shapes are replaced by a fixed notice; this is heuristic and the bridge filters first. `POST /api/bridge/heartbeat` optionally accepts `{instructions:{ready, reason?: disabled|launcher_down|locked|busy}}` and returns `instructionsEnabled`, `mediaEnabled`, `previewsEnabled` and `sourceRevision` with or without that body.

**Screen.** A first-screen "작업 지시" section opens a composer (text, target from today's pick or the content list, end level 초안/리뷰 반영/게시 직전 패키지/앱 병합 전), then a preview with one confirmation. Draft and preview state live outside the 30-second briefing refresh; each preview gets one idempotency key and the send button is locked while in flight. A 401/403 removes the draft. The list shows the session name as plain text on running, done and failed cards, and Mac 대기 중(이유), 실행 중 · 세션, 지연 (running longer than 60 minutes; the slot stays occupied), 답 필요 with the question and the Paseo session to open, 완료/실패/취소됨/만료됨, elapsed time and the summary as plain text; queued rows can be cancelled. When the server switch is off the composer is disabled with the reason. The today card's primary action is "이 항목으로 지시"; the Paseo request copy moved into the collapsed "Paseo로 직접 이어가기".

**Validation.** `npm run test:instructions` bundles the real `lib/api.ts` into Miniflare with in-memory D1 per scenario: missing header, any signed-in user reading/creating/listing/cancelling the shared queue, switch off, CSRF variants, 413/415/400 cases, rate/day/queue limits, idempotency (resend before limits, 409, cancelled/expired keys, concurrent double tap), concurrent claims at max active 1 and 2, cancel vs claim race in both orders, transition and field rules, masking, expiry, heartbeat readiness, one event per transition, no requester ids in about 300 responses or worker output. `npm run test:instructions-ui` (local dev server, `INSTRUCTIONS_ENABLED=true`) covers 390/1280px compose→preview→confirm→list, refresh during preview/draft (including the real 30-second timer), double tap → one POST and one row, cancel, today prefill, a bridge-API roundtrip to needs_user/done/failed, every badge, switch off and auth loss.

# 정본 스마트 에디터

마크업 정본은 [마크업 편집기 연결](markup-editor-integration.md)을 따른다. 대시보드의 정본 스마트 에디터 열기 버튼이 앱 내부 창과 loopback 서버를 직접 연다. 아래 인라인 본문/레이어 JSON·4320 설명은 이전 형식 전용이다.

사용자는 이미 만든 정본의 사진·콜라주·문단·강조를 실제 배치로 보면서 본문을 직접 고친다. 별도 `BlogDraft` 복사본이나 검토 파일 업로드 화면을 정본 편집기로 취급하지 않는다.

## 실행과 화면

`npm run build` 후 `npm run blog:editor -- /absolute/path/to/private-config.json`을 실행한다. 설정은 콘텐츠 작업공간 또는 개인 임시 폴더에 두며 앱 소스에 개인 경로·원고를 복제하지 않는다.

```json
{
  "canon": "/absolute/content/article.md",
  "layers": "/absolute/workspace/layers",
  "layout": "/absolute/workspace/publishing/smarteditor-draft-layout.html",
  "media": "/absolute/content/media",
  "port": 4320
}
```

`http://127.0.0.1:4320/?blogEditor=1`에서 실제 정본을 연다. 앱의 블로그 화면에도 이 로컬 편집기로 가는 링크가 있다. 서버는 설정으로 지정한 정본 1개만 편집한다. 기존 4318 워크플로 서버나 실행 중인 Electron 앱을 재시작하지 않는다.

- 왼쪽: 기존 묶음 경계·이름으로 이동.
- 가운데: 기존 미리보기 CSS·글꼴, 사진·콜라주, 문단·부분 강조. 문단을 클릭해 직접 수정하고 구절 선택 후 굵게·글자색·배경·서식 제거. Enter는 같은 문단 내 줄바꿈이다.
- 오른쪽(보조): 선택 묶음의 검토 요약, 실행 상태, 화면 검토, 제안 목록(상태·이유·`본문에서 보기`). 적용·현재 유지 판단은 본문 대상 문구에 바로 그려진 diff와 작은 팝오버에서 한다(~~문장 아래 제안 카드~~는 2026-11-03에 대체됨, [본문 인라인 diff 제안](#본문-인라인-diff-제안--2026-11-03)). 선택 이력은 현재 화면에만 보관되며 본문 변경은 저장해야 정본에 남는다.
- 상단: 저장 상태, 정본 저장(바로 저장), 모바일/PC 폭, 이 묶음/변경분 검토. 마크업 원고는 [자동 저장·실시간 동기화](#자동-저장실시간-동기화--2026-11-05)로 동작하며 다시 불러오기 단계가 없다(옛 레이어 형식만 수동 저장·다시 불러오기를 유지). 편집이나 시간 경과는 평가를 실행하지 않는다.

현재 지원 편집 범위는 기존 제목·문단의 문장·줄바꿈·부분 강조다. 사진과 묶음 배치는 기존 레이어를 그대로 표시하며, 분석된 사진을 넣는 것은 [사진 고르기](#사진-고르기--2026-11-04)로 할 수 있다. 사진 삭제·콜라주 재구성·새 문단/묶음 생성은 아직 제공하지 않는다. 기존 묶음 통째 삭제는 [묶음 삭제·저장 단축키](#묶음-삭제저장-단축키--2026-11-03)를 따른다. 네이버 장소 지도·블로그씨 카드는 기존 자리 표시다.

## 저장 계약

정본의 `### 본문`에서 문단 ID T1…을 기존 grouping/bundle 레이어와 대조한다. 문단 매핑 불일치·누락/겹침·다른 세션의 변경은 저장을 거절한다. `### 제목`과 변경한 본문 문단만 수정하고 frontmatter·사진 지시문·비공개 메모·나머지 문단은 보존한다. 해당 문단의 `emphasis-layer.json`과 미리보기 HTML을 함께 갱신하며 `layers/editor-backups/`에 원본을 남긴다. 새 독립 초안은 생성하지 않는다.

입력 revision은 정본·묶음·블록 순서·강조 파일의 지문이다. 저장 직전 다시 대조하고 각 파일 교체 직전 외부 변경을 확인한다. 실패 시 자신이 쓴 내용만 복구한다. 여러 파일의 교체 전체가 파일시스템 단일 원자 연산인 것은 아니므로 프로세스 강제 종료 후에는 백업과 실제 파일 상태를 확인한다. 기존 엔진의 compose.py·pipeline-state.json·리뷰 산출물을 UI에서 임의 실행/갱신하지 않는다. 텍스트 레이어와 엔진 상태는 엔진 다음 실행에서 갱신한다.

## 명시적 검토 요청과 엔진 경계

검토 버튼은 편집 내용이 있으면 정본 저장 성공 후 `layers/editor-requests/<uuid>.json`을 만든다. 실패한 저장으로는 요청을 만들지 않는다. 요청에는 `kind:blog.editor.review-request`, `status:pending`, `trigger:user`, `basedOn` 정본 revision, `bundleIds`, 정본/레이어 경로와 시간이 들어 있다. 변경분은 해당 묶음과 이웃 전환을 포함한다. 실제 재시작 단계 결정·에이전트 실행·새 리뷰 생성은 별도 엔진이 맡는다. 현재 소비자가 연결되지 않았으므로 UI는 **엔진 처리 대기**로 표시하며 평가 완료를 가장하지 않는다. 사용자가 JSON을 수동으로 옮길 필요는 없다.

기존 리뷰의 textHash는 Python 합성기의 텍스트 해시와 대조한다. 이것만으로 사진/서식까지 최신이라고 주장하지 않는다. 새 엔진의 전체 묶음 fingerprint 계약과 요청 소비·상태 갱신 연결은 후속 작업이다.

## 확인

합성 콘텐츠를 사용하는 테스트에서 실제 파일 저장·강조 반영·미리보기 반영·비공개 메모/사진/다른 문단 보존·동시 수정 차단·명시적 검토 큐 생성을 검사한다. 브라우저에서는 contenteditable 입력과 실제 선택 구절 서식 변경, 저장/새로고침, 모바일 폭, 충돌 후 사용자 변경 보존을 확인한다. 실제 콘텐츠는 읽기 및 개인 임시 복사본 검증만 하며 검증용 문장을 정본에 저장하지 않는다.


## Codex SDK 문안 검토

정본 저장 후 **Codex로 선택 묶음 검토**를 누르면 공통 [워크플로 서버](workflows.md#codex-sdk-execution--2026-11-01)가 저장된 로그인으로 SDK를 실행한다. 데스크톱 앱에서는 앱이 [워크플로 서버를 내장](workflows.md#desktop-embedded-server--2026-11-03)하므로 따로 실행하지 않는다. 독립 실행 편집기(`npm run blog:editor`)는 워크플로 서버를 함께 실행해야 한다. 편집기 서버는 같은 origin의 요청을 전달한다. 기존 엔진 작업 폴더에 남기는 검토 요청과 별개의 명시 실행 경로다.

결과는 제안으로 표시하고 자동 반영하지 않는다. 요청 후 정본 revision이나 저장 전 편집이 바뀌면 적용을 막는다. **SDK 제안 적용**은 화면에 반영하고 **정본 저장**은 기존 저장·백업 검증을 수행한다. 이번 SDK 검토는 전달된 문안·기준에 한정되며 사진·완성 화면을 검토했다고 주장하지 않는다.

## 디자인·서식 보강 — 2026-11-01

1080px 이하에서는 검토를 원고 맨 아래에 놓지 않고 **검토 보기**로 여는 패널로 표시한다. 닫기·바깥 영역·Escape로 닫으며 키보드 포커스는 패널 안에서 이동하고 닫으면 원래 버튼으로 돌아간다. 모바일 묶음 목록은 **글의 흐름**으로 펼친다. 상단 도구 높이를 측정해 본문 이동·고정 패널 위치에 사용한다.

본문의 구절을 선택하면 현재 글자 크기·굵기·색이 도구에 표시된다. 글자 크기는 기존 공통 SmartEditor 단계(11–45px), 글자색은 기본/적갈/갈색/하늘/초록 및 직접 색 선택, 배경색은 노랑/살구/연회색 및 직접 선택을 지원한다. **배경색만 지우기**와 **서식 지우기**를 구분한다. 팔레트·크기 메뉴로 포커스가 옮겨져도 원래 구절에 적용하며, 크기 변경이 기존 색·굵기·배경을 제거하지 않는다. 제목 서식과 문단 정렬·글꼴 교체는 이 추가 범위가 아니다.

기존 강조 제안은 **현재 서식 / 제안 서식**을 구절·크기·색·배경·굵기로 비교한다. 본문의 실제 글꼴 파일과 문단의 기본 크기를 재사용하고, 제안 이유와 묶음 평가 요약은 펼쳐 읽는다. 글자 스타일은 정본·강조 레이어 저장에 포함되며 검토 버튼을 누르지 않은 편집은 평가를 실행하지 않는다.

검증: 선택→색상→24px→굵게→배경만 제거→정본 저장/재열기, 서식 전후 표시, 1024px 검토 패널·Escape/포커스 복귀, 390px 묶음 접기/가로 넘침, 기존 정본 저장 충돌 보호 및 SDK 명시적 적용 회귀를 합성 콘텐츠로 확인했다. 실제 원고는 화면 검수만 한다.

기존 미디어가 심볼릭 링크인 경우 서버 설정의 `assetFiles`에 실제 원본 파일 경로를 개별 등록할 수 있다. 등록된 블록 이름과 등록된 원본 대상이 모두 일치할 때만 제공하며, 다른 대상으로 바뀐 링크는 거절한다. 이번 실제 화면 검수에서 콜라주 사진 2장의 기존 원본 링크를 이 방식으로 연결했다. 원본 이동·복제·이미지 편집은 하지 않았다.

## 외부 실행기 묶음 리뷰 — 2026-11-02

앱 안의 Codex SDK 대신 Claude Code Workflow나 Codex 서브에이전트가 같은 묶음 리뷰 계약을 실행할 수 있다. 바뀌는 것은 실행 주체뿐이다. 입력(`reviewMaterials`: 범례 + 노트 `## 규칙` + 원고, `reviewGuidance`, 사용자 주석), 결과 검증(`validateMarkupReview`), 저장(`storeMarkupReviews`가 요청한 묶음만 교체), 신선도 판정은 앱과 같다. 실행 절차와 역할 지침은 콘텐츠 작업공간의 리뷰 루프 스킬에서 관리한다.

```sh
node --import tsx scripts/blog-review.ts projects
node --import tsx scripts/blog-review.ts status <project-id>
node --import tsx scripts/blog-review.ts prepare <project-id> <new-packet-dir> [--changed | --all | --bundles B1,B2]
node --import tsx scripts/blog-review.ts import <project-id> <packet.json> <result.json> --provider <name> [--run <id>]
```

- 프로젝트는 `blog-projects.json`에 등록된 ID로 고른다. `REELS_DASHBOARD_USER_DATA`로 user-data 위치를 바꿀 수 있다. markup 형식이고 `review` 경로가 있는 프로젝트만 지원한다.
- `prepare`는 새 패킷 폴더에 `packet.json`(앱 요청과 같은 `markupReviewInput`과 묶음 해시), `source.md`, `guidance.md`, `bundles/<ID>.json`(앞뒤 묶음 원문, 허용 문단 ID, 기존 강조 구절, 해당 주석, 문단 ID enum을 넣은 결과 스키마)을 만들고, 빈 `out/` 폴더도 만든다. 기본값 `--changed`는 검토가 없거나 텍스트가 바뀐 묶음만 고른다. 공개 저장소 안의 경로는 거부한다. 같은 폴더를 두 번 쓰지 않는다.
- `import`는 패킷과 원고가 같은지 확인하고, 앱과 같은 검증을 거쳐 `review` 파일에 저장한다. `requests/<id>.json`에 완료 영수증(`provider`, `runId` 포함)을 남기며, 이 영수증은 앱 worker가 다시 처리하지 않는다. 같은 패킷은 한 번만 가져온다. 검토 중 원고가 바뀌면 `stale`로 기록한다. 원고 파일은 수정하지 않는다.
- 외부 실행기에는 화면 캡처가 없다. `visual.status`가 `unverified`가 아니면 가져오기를 거부하므로, 이 경로의 결과는 `passed`가 될 수 없다. 화면 판정은 기존 앱 검토(360/390/430px 캡처)로 따로 받는다.
- `status`는 묶음별 판정, 실행 주체, 텍스트·화면 신선도, 남은 제안 수(필수/권장/관찰), 다시 검토가 필요한지를 반환한다.

검증: 합성 원고로 패킷 생성, 공개 저장소 경로 거부, 화면 통과 주장 거부, 가져오기 후 에디터 검토 목록 표시, 중복 가져오기 거부, 원고 무변경, 원고 변경 뒤 재검토 대상 선택을 확인했다(`tests/unit/blog-external-review.test.ts`). 기존 worker 저장 로직을 공용 함수로 옮긴 뒤 worker 테스트도 통과했다.

## 본문 내 제안 검토 — 2026-11-02

> **2026-11-03 대체됨:** 아래의 문단 아래 제안 카드(`.rv-stack`/`.rv-card`)와 카드 중심 설명은 [본문 인라인 diff 제안](#본문-인라인-diff-제안--2026-11-03)으로 바뀌었다. 적용 경로·내용 지문(`sig`) 대조·리뷰 UI가 정본에 섞이지 않는 원칙은 그대로이고, 표시 방식과 키 동작만 달라졌다. 기록 보존을 위해 원문을 남긴다.

- 텍스트 제안은 대상 문구 위치에 바뀌는 부분만 표시한다(삭제는 취소선·붉은 배경, 삽입은 카드의 diff). 문단을 복제하지 않는다. 서식 제안은 문단 글꼴·크기에 각 run의 색·배경·굵기·크기를 입힌 현재/제안 샘플을 문구 근처에 나란히 보여 준다.
- 각 카드에 `적용`·`현재 유지`·`이유`가 있다. 적용은 기존 적용 경로(대상 문구 검증·오래된 제안 잠금·동시 편집 보호)를 다시 거쳐 편집 내용에 들어가고, 저장·백업은 기존과 같다. 현재 유지는 본문을 바꾸지 않는다. 결정한 카드는 사라진다.
- 적용이나 직접 편집 뒤 같은 문단의 나머지·겹치는 제안을 다시 검증한다. 대상이 바뀌었거나 위치를 하나로 찾지 못하면 본문에 표시하지 않거나 잠긴 카드로 이유만 보여 주고 적용을 막는다.
- 사진·배치 의견처럼 문장 치환이 아닌 제안은 해당 묶음(언급된 사진이 있으면 그 사진) 근처에 의견 카드로 둔다.
- 검토 UI는 리뷰 전용이다. 본문 표시는 CSS Custom Highlight와 `[data-tid]` 문단 밖 형제 카드로만 그리며, 편집기 iframe에 `proposals` 메시지가 올 때만 생긴다. 정본·저장 본문·파생 미리보기·발행 결과·화면 캡처 창에는 섞이지 않는다.
- 모바일에서는 카드가 대상 문단 바로 아래에 종이 폭 안에서 줄바꿈되며 가로 스크롤을 만들지 않는다.
- 링크는 본문에 라벨만 보이므로, 대상이 링크 주소나 링크 글자 일부에 걸친 제안은 위치를 표시하지 않고 잠근다. 링크 전체를 포함하는 제안은 링크 라벨 전체를 대상으로 표시한다.
- 적용·현재 유지 클릭은 화면에 표시했던 제안의 내용 지문을 함께 보낸다. 재검토로 같은 ID의 제안 내용이 바뀌었으면 그 클릭을 거부하고 다시 확인하도록 안내한다.
- 키보드로 결정하면 포커스가 다음 제안 카드로 이동한다. 펼쳐 둔 `이유`는 편집 중 다시 그려도 유지된다. `이유`와 패널의 `제안 이유`에는 잘리지 않은 원문·제안 전문이 있다.

검증 (2026-11-02, 합성 원고만 사용): `typecheck`, `check:architecture`, `audit:public`(551 entries)가 통과했다. Homebrew Node 26 기준 `npm test` 197/197이 통과했고, 그중 `inline-review` 단위 테스트는 18개다. 브라우저 검증은 headless로 `canonical-inline-review`(2개), `canonical-blog`, `canonical-formatting`, `canonical-save-status`(2개), `canonical-sdk`, `markup-layout`을 실행해 8/8 통과했다. `canonical-inline-review`와 `canonical-save-status`를 3회 반복해 12/12 통과했다. `npm run build` 뒤 Electron background QA(`markup-editor`, `blog-scroll`)는 4개 통과, 2개 skip이다. skip한 것은 실제 원고 확인과 live visual review로, `REELS_MARKUP_CONFIG`가 필요해 실행하지 않았다. 확인한 항목은 본문 diff 표시, 적용과 현재 유지, 한 문단의 여러 제안 재검증, 대상 변경 뒤 적용 차단, 링크 내부 대상 차단, 재검토 뒤 오래된 클릭 거부, 키보드 포커스 이동, `이유` 펼침 유지, 저장 뒤 다시 열었을 때 원고에 리뷰 UI가 없는지다. Playwright 웹 spec은 Node 22(nvm)로 실행하면 `canonical-sdk`가 OpenTelemetry 로드 오류로 수집되지 않는다. 이 오류는 이번 변경과 관계없다.

## Tab 추천 — 2026-11-03

마크업 정본 편집기에 Cursor식 키보드 추천을 더했다. 두 층으로 나뉘며, 둘 다 사용자가 키를 누르기 전에는 본문을 바꾸지 않는다.

### 1층: 검토 제안을 Tab으로 넘기기

> **2026-11-03 일부 대체됨:** 이 층의 안내 상자 위치·표시 조건·카드 언급은 [본문 인라인 diff 제안](#본문-인라인-diff-제안--2026-11-03)의 활성 제안 팝오버와 키 표가 최신이다. 아래는 당시 기록이다.

- 새 검토 경로는 없다. [본문 내 제안 검토](#본문-내-제안-검토--2026-11-02)의 제안 가운데 현재 문단에 위치가 확정된 제안(적용 가능)만 대상이다.
- 커서가 그런 제안이 있는 문단에 있으면 대상 아래에 작은 안내 상자(`role=status`, `aria-live=polite`)가 뜬다. 바뀌는 부분만 보여 주는 짧은 diff와 `Tab 적용 · Esc 유지 · Shift+Tab 이전`, 그리고 그 묶음을 다시 검토하는 `다시 검토` 버튼이 있다. 안내 상자는 종이 폭 안에 머문다. 커서 위치를 포함하는 제안이 우선이고, 없으면 같은 문단에서 커서 뒤의 가장 가까운 제안을 고른다.
- **Tab**: 커서가 제안 위(또는 바로 옆)에 있으면 적용한다. 적용 경로는 카드의 `적용`과 같아서 대상 문구 검증, 오래된 제안 잠금, 내용 지문 대조를 그대로 거친다. 적용한 뒤 문서 순서상 다음 제안의 시작 위치로 커서를 옮긴다. 다음 위치는 갱신된 제안 목록으로 다시 계산하며 이전 offset을 그대로 쓰지 않는다. 커서가 제안 위에 있지 않으면 첫 Tab은 적용하지 않고 다음 제안으로 이동만 한다.
- **Shift+Tab**: 이전 제안으로 이동한다. **Esc**: 커서가 제안 범위 안에 있을 때만 그 제안을 `현재 유지`로 처리하고(본문 변경 없음) 다음으로 이동한다. 커서 뒤의 제안이 안내 상자에 보이기만 하는 상태에서는 Esc를 가로채지 않는다. 보이기만 하는 제안이 실수로 숨겨지지 않게 하려는 것이다.
- 안내 상자는 활성 제안이 없으면 DOM에서 지운다. 안내 문구는 계속 남는 별도 live region(`data-review-ui="live"`)으로도 읽어 준다. 대상이 화면 밖이면 그만큼만 스크롤한다.
- 링크 일부를 겨냥한 제안처럼 잠긴 제안은 이동 대상에서 빠진다. 해당 카드에는 기존처럼 이유가 표시된다.
- 앞이나 뒤에 남은 제안이 없으면 Tab·Shift+Tab·Esc를 가로채지 않으므로 포커스가 갇히지 않는다. 한글 조합 중(`isComposing`, keyCode 229)이거나 편집이 잠겼을 때는 키를 무시한다.

### 2층: 직접 요청하는 회색 추천

- 타이핑만으로는 요청하지 않는다. 상단의 **✦ 추천 받기** 버튼이나 본문 안의 **⌥\\**(Alt+Backslash)로 요청할 때만 커서 위치에 이어 쓸 문장을 받는다. 마크업 정본에서만 쓸 수 있고, 이전 형식에서는 버튼이 비활성이며 이유를 툴팁으로 알려 준다.
- 기다리는 동안 버튼은 회전 아이콘과 `추천 중… (Esc 취소)`로 바뀌고, 본문 커서 자리에 작은 회전 표시(`추천을 기다리는 중`)가 나타난다. 일부러 기다리게 하는 흐름이다. Esc나 새 요청은 진행 중인 요청을 취소한다.
- 응답을 기다리는 사이 문단 내용, 커서 위치, 선택 범위(시작 위치·선택 여부), 포커스, 문서 revision 중 하나라도 바뀌면 결과를 버리고 `본문이 바뀌어 추천을 버렸어요. 다시 요청해주세요.`를 보여 준다. 추천이 비어 있으면 `이 위치에 추천할 문장이 없어요.`를 보여 준다.
  - 포커스는 응답 시점의 실제 포커스로 판단한다. 기다리는 동안 포커스가 문단 밖(프레임 안의 다른 버튼·메모 배지 등)으로 가면 바로 취소하고, 늦게 온 응답이 포커스를 문단으로 되돌리지 않는다. 다른 앱으로 전환하는 것만으로는 취소하지 않는다.
  - 커서 끝이 같아도 Shift+방향키 등으로 선택을 만들었다면 결과를 버리고, 만든 선택은 그대로 둔다.
  - 링크는 본문에 라벨만 보여서 라벨 안의 모든 위치가 링크 시작 위치 하나로 계산된다. 그래서 커서가 링크 글자 안에 있으면 요청하지 않고 `링크 글자 안에서는 추천할 수 없어요. 링크 앞이나 뒤에 커서를 두고 다시 요청해주세요.`를 보여 준다. 기다리는 사이 커서가 링크 글자 안으로 옮겨져도 결과를 버린다.
  - 호스트 입력란에서 한글 조합을 끝내려고 누른 Esc(`isComposing`, keyCode 229)는 진행 중인 요청을 취소하지 않는다.
- 결과는 커서 자리에 회색(`#9aa29c`) 글자로 표시된다. 이 표시는 편집할 수 없고 클릭도 받지 않는다(`data-review-ui="ghost"`). 화면 낭독기에는 별도 live region으로 추천 문장을 읽어 준다. 후보는 최대 3개다.
  - **Tab**: 추천 전체를 일반 입력처럼 넣는다. 되돌리기(⌘Z)가 되고, 저장 전 변경으로 표시된다.
  - **⌘/Ctrl+→**: 다음 어절 하나(뒤따르는 공백 포함)만 넣고, 나머지는 회색으로 남긴다.
  - **⌥]** / **⌥[**: 다른 후보로 바꾼다. 순번(`추천 1/3`)은 문단 아래 작은 추천 막대에 보인다. 막대에는 `수락`·`한 어절`·`다른 추천`·`다시`·`닫기` 버튼과 키 안내가 있다. 회색 글자는 클릭을 받지 않으므로 마우스·터치로는 이 막대로 수락한다.
  - **⌥\\**: 새로 요청한다. **Esc**: 추천을 닫는다.
  - 추천의 첫 글자와 같은 글자를 치면 그 글자만큼 추천이 줄어든다. 고른 추천의 마지막 글자까지 치면 추천이 끝나며, 그 추천으로 시작하는 더 긴 다른 후보가 이어서 뜨지 않는다. 다른 글자를 치거나 커서를 옮기거나 포커스를 잃으면 추천을 닫는다. 잠금, 본문 교체, 다시 불러오기·저장(프레임 재생성), 서식 적용, 메모 작성, 한글 조합 시작 때도 닫는다.
  - 제안 카드 다시 그리기 때는 닫지 않는다. 다시 그리기는 문단 안을 건드리지 않고 위치 계산도 회색 추천을 건너뛰기 때문이다. 제안이 있는 문단에서 이어 받기를 하면 입력마다 다시 그리기가 일어나므로, 이때 닫으면 추천이 바로 사라진다.
  - 한글은 조합이 시작되면 추천이 닫히므로 이어 받기가 되지 않는다. 라틴 문자·숫자·구두점·공백만 이어 받는다. 모바일 가상 키보드도 조합 입력이라 막대 버튼으로 수락한다.
  - 표시할 때 나눈 텍스트 노드는 닫을 때 다시 합친다. 추천을 보이고 닫기만 해서는 정본 source나 저장 상태가 바뀌지 않는다.
- 추천을 만드는 동안 서버(`POST /api/blog/suggest`)는 파일을 쓰지 않는다. 저장 전 문단 원문과 plain-text 커서 위치를 받아 앞뒤 문장, 이웃 묶음 마크업, 노트의 `## 규칙`, 검토 기준, 제목, 이웃 문단의 사람 메모(명령이 아닌 데이터)를 묶어 워크플로 서버의 `suggest-inline` 동작([워크플로 문서](workflows.md#inline-suggestions-suggest-inline--2026-11-03))을 동기로 호출한다. 마크업 기호·줄바꿈을 지우고, 커서 뒤 문장을 되풀이하는 후보와 중복 후보를 걸러 낸다. 길이는 240자 이하로 자른다. 엔진에 연결하지 못하면 `추천 엔진에 연결하지 못했어요. 워크플로 서버가 실행 중인지 확인해주세요.`를 보여 준다.
- 회색 추천·회전 표시·안내 상자는 리뷰 UI(`data-review-ui`)라서 직렬화·plain-text 매핑·메모 위치 계산에서 빠진다. 서식 적용과 메모 작성 전에도 회색 추천을 먼저 지운다. 받아들인 글자만 정본·저장 본문·미리보기·발행 결과에 남는다.
- 상단 도움말 줄에 Tab 키 사용법을 짧게 덧붙였다.
- 추천은 워크플로 서버의 새 `suggest-inline` 동작을 쓰므로, 이 변경 이전에 띄운 워크플로 서버(기본 4318)는 다시 시작해야 한다. 다시 시작하지 않으면 원문 오류 대신 `실행 중인 워크플로 서버가 이전 버전이에요…` 안내가 보인다. 데스크톱 앱은 이전 버전 서버를 감지해 워크플로 화면에도 같은 안내를 띄운다([내장 서버](workflows.md#desktop-embedded-server--2026-11-03)).
- 끝 공백 처리: 모델이 문장 중간 이어 쓰기 끝에 공백을 붙여 돌려주면(예: `빵을 사서 ` 뒤에 `집에…`) 그 공백을 보존한다. 실제 엔진 확인에서 이 공백이 잘려 `사서집에`가 되는 문제를 발견해 고쳤다.

검증(2026-11-03, 합성 원고만 사용):

- `npm run build` 후 Electron background QA(`markup-editor`, `blog-scroll`)는 4개 통과, 2개 건너뜀이었다. 건너뛴 2개는 실제 원고와 live 시각 검토 테스트로, 설정이 필요하다.
- 스크린샷으로 데스크톱(1440px)과 모바일(390px)의 안내 상자, 회전 표시, 회색 추천을 확인했다. 안내 상자는 대상 바로 아래 제안 카드의 윗부분을 일부 가린다. 포인터는 통과하지만 디자인을 다듬을 여지가 있다.
- 후속 수정(2026-11-03): 리뷰에서 확인된 다섯 가지를 고쳤다. ① 기다리는 동안 포커스가 문단을 떠나도 늦은 응답이 회색 추천을 띄우고 포커스를 되돌리던 문제, ② 링크 글자 안의 커서가 모두 링크 시작 위치로 계산돼 위치 변경을 알아채지 못하던 문제, ③ 호스트 입력란에서 한글 조합을 끝내는 Esc가 요청을 취소하던 문제, ④ 고른 추천을 끝까지 쳤을 때 더 긴 다른 후보가 이어서 뜨던 문제, ⑤ 기다리는 동안 같은 끝 위치로 선택을 만들면 결과가 적용되며 선택이 풀리던 문제다. `canonical-tab-suggest`에 이 다섯 경우를 확인하는 브라우저 테스트 1개를 추가했다. 수정마다 그 수정만 되돌려 실행하면 이 테스트가 실패하는 것도 확인했다. 포커스 확인을 응답 시점과 `focusout` 즉시 취소 두 곳에서 하는데, `focusout` 즉시 취소만 되돌렸을 때는 응답 시점 확인이 같은 결과를 막아서 테스트가 통과했다.
- 후속 수정 뒤 다시 확인한 결과: `typecheck`, `check:architecture`, `audit:public`(567 entries)이 통과했고, `npm test`는 220/220 통과했다(이번 테스트는 웹 spec이라 단위 테스트 수는 그대로다). `npm run build:web` 뒤 같은 웹 spec 7개 파일이 13/13 통과했고, `--repeat-each 3`으로 39/39 통과했다. `npm run build` 뒤 Electron background QA(`markup-editor`, `blog-scroll`)는 4개 통과, 2개 건너뜀으로 이전과 같다. 데스크톱·390px 스크린샷을 다시 찍었다. 실제 엔진 지연 측정은 다시 하지 않았다(아래 수치는 이전 측정이다).
- 실제 Codex(저장된 로그인, 기본 모델, effort low)로 별도 포트의 워크플로 서버를 띄워 `suggest-inline`을 확인했다. 응답이 온 호출은 5.3~12.2초 걸렸다. 같은 시간대에 응답 이벤트 없이 90초 시간 초과로 끝난 호출도 많았다. 같은 시간에 일반 `codex exec`도 90초 동안 응답하지 않아, 백엔드나 계정 쪽 지연으로 판단했다. 커서 뒤에 새 사실이 필요한 위치(문단 끝)에서는 지어내지 않도록 빈 목록을 돌려주는 경우가 많았다.

## 기본 스티커 배치 — 2026-11-03

마크업 정본 편집기의 **스티커** 버튼에서 네 가지 용도를 선택하고 문단·사진 사이에 자리를 놓는다. 실제 네이버 기본 스티커는 이관 시 선택하며, 대시보드는 위치·선택 메모와 자리 표시를 저장한다. 배치 메모 복사, 과도한 사용 안내, 위치 보기·이동·삭제를 지원한다. [사용법과 저장 계약](blog-stickers.md).

## 묶음 삭제·저장 단축키 — 2026-11-03

- **⌘/Ctrl+S**: 본문(iframe) 안이나 바깥 어디서든 정본 저장 버튼과 같은 즉시 저장을 실행한다. 삭제·사진의 유예도 건너뛴다. 변경이 없으면 `저장할 변경이 없어요.`만 표시한다. IME 조합 중에는 무시한다.
- **묶음 삭제**(markup 원고만): 본문에서 묶음의 글 밖(이름표·사진 등)을 클릭하면 묶음 테두리가 표시되고 Delete/Backspace로 지운다. 글 안에 커서가 있을 때 Backspace는 평소처럼 글자만 지운다. 왼쪽 글의 흐름 항목에 포커스를 두고 Delete를 누르거나 도구줄 **묶음 삭제**를 눌러도 된다. Esc는 묶음 선택을 해제한다.
- 삭제는 화면에서 먼저 숨기고 8초 유예 동안 **삭제 취소 (n)**으로 마지막 삭제부터 되돌린다. 유예가 끝나거나 ⌘S를 누르면 `deleteBundles`로 서버에 전달되고 해당 묶음(안의 문단·사진·스티커 포함)이 정본에서 빠진다. 저장된 뒤에는 취소 버튼이 사라지고 이전 내용은 `.history`에 남는다.
- 마지막 남은 묶음은 지울 수 없다. 지운 묶음의 앞뒤 묶음은 변경분 검토 대상에 추가된다. 지운 묶음의 기존 리뷰 기록과 사용자 주석 파일은 수정하지 않는다.

검증: headless `canonical-bundle-delete` 2개(프레임/호스트 ⌘S, 글 안 Backspace 보호, 이름표 선택 후 Delete·Backspace, 삭제 취소, 저장 후 정본에서 제거, 글의 흐름 Delete, 마지막 묶음 보호)와 기존 canonical·markup-layout spec, 단위 테스트, 타입·FSD 검사.

## 본문 인라인 diff 제안 — 2026-11-03

문단 아래에 쌓이던 제안 카드를 없애고, 텍스트 제안을 대상 구절 바로 그 자리에 diff로 그린다(Cursor식). 앞선 [본문 내 제안 검토](#본문-내-제안-검토--2026-11-02)의 카드 설명과 [Tab 추천](#tab-추천--2026-11-03) 1층의 안내 상자 설명은 이 절로 대체된다. 제안은 여전히 사용자가 명시적으로 적용하기 전에는 원고를 바꾸지 않는다.

### 본문에 그려지는 모습

- **텍스트 제안**: 지워질 글자는 빨간 취소선(CSS Custom Highlight `rv-del`, DOM은 바뀌지 않음), 들어갈 글자는 초록 글자·연초록 배경·밑줄로 그 위치에 나타난다. 삽입 조각마다 비어 있고 편집할 수 없는 `<span data-review-ui="ins">`를 두고 글자는 CSS로만 그리므로 선택·복사·저장에는 포함되지 않는다. 삭제·삽입 조각이 문단 글자 위치와 맞지 않으면(예: 링크 경계) 대상 구절 전체를 취소선으로 긋고 제안 문구를 그 뒤에 한 번 표시한다.
- **겹친 제안**: 같은 문단에서 범위가 겹치는 텍스트 제안은 첫 제안만 인라인으로 그린다. 나머지는 `✦ 겹친 제안` 표시로 두고, 앞 제안을 적용하거나 유지한 뒤 호스트가 다시 검증하면 그때 인라인으로 바뀐다. 겹친 제안 표시에서는 적용할 수 없다(팝오버 `적용` 비활성, Tab은 다음으로 이동). 화면에 그려진 diff와 다른 제안이 적용되는 일을 막기 위해서다.
- **diff로 못 그리는 제안**은 작은 표시(`data-review-ui="marker"`)로 둔다.

  | 표시 | 대상 |
  |------|------|
  | `✦ 서식` | 서식 제안. 대상 구절은 점선 밑줄 배경(`rv-target`)으로 표시 |
  | `✦ 메모` | 구성 의견. 문단이 있으면 문단 끝, 사진·배치 의견은 해당 사진/묶음 옆 별도 줄(note-row) |
  | `⚠ 확인 필요` | 적용할 수 없는 제안(위치를 하나로 못 찾음, 링크 일부 겨냥 등) |
- **본문이 바뀐 제안**(대상 문구가 달라진 상태)은 본문에 아무것도 그리지 않는다. 오른쪽 패널의 제안 목록에 `본문 변경됨` 칩으로 이유를 보여 준다.

### 활성 제안과 팝오버

커서가 제안 범위 안이나 바로 옆에 있거나, Tab으로 이동했거나, 제안 구절·표시를 클릭/탭했거나, 패널에서 `본문에서 보기`를 누르면 그 제안이 활성이 된다. 활성 제안은 노란 배경(`rv-focus`)으로 강조하고, 범위 아래에 작은 팝오버(`data-review-ui="hint"`) 하나가 뜬다.

- 위치: 종이 폭 안에 맞추고, 아래 공간이 모자라 잘릴 것 같으면 위로 뒤집는다. 대상 줄을 가리지 않는다. 종이 폭이 520px 미만인 모바일에서는 종이 폭 전체를 쓰는 시트처럼 펼친다.
- 내용: 제안 종류·심각도, 바뀌는 부분 요약(서식은 현재/제안 샘플), 막혀 있으면 그 이유. 버튼은 `적용`(Tab)·`유지`(Esc)·`이유`(전문 펼침)·`다시 검토`다. 막힌 제안은 `적용`이 비활성이고, 구성 의견은 `적용`과 `이유` 없이 `유지`만 쓴다. 키 안내(`Tab 다음`, `Shift+Tab 이전`)는 필요할 때만 보인다.
- 팝오버는 버튼과 `이유` 글만 포인터를 받는다. 나머지 영역을 누르면 그 아래 본문 글자에 그대로 닿으므로 이웃 문장을 가려도 클릭·커서 이동이 막히지 않는다. 표시(`✦`/`⚠`) 팝오버는 표시뿐 아니라 그 표시가 가리키는 구절도 피해서 놓는다.
- Tab·자동 이동·`본문에서 보기`로 문단이 없는 사진·배치 메모에 가면 그 메모의 묶음을 호스트에 선택(`select`)으로 알린다. 오른쪽 패널과 `선택 묶음 검토`가 이전 묶음에 남지 않는다.
- 키보드로 팝오버 버튼에 가려면 `⌥/Alt+↓`를 누른다(첫 사용 가능 버튼으로 이동, 그 안에서 Tab으로 버튼 사이 이동). 팝오버 안에서 `Esc`는 결정 없이 원래 커서 위치로 돌아간다.
- 390px 등 좁은 화면에서 표시의 탭 영역은 줄 높이를 바꾸지 않고 세로 36px 이상으로 넓힌다. 팝오버 버튼도 36px 이상이다.
- 활성 제안이 없으면 팝오버는 DOM에서 지워진다. 같은 내용은 `data-review-ui="live"` 영역으로 읽어 준다. 펼친 `이유`는 다시 그려도 유지된다.

### 키 동작

| 키 | 상황 | 동작 |
|----|------|------|
| Tab | 커서가 적용 가능한 활성 제안 위 | 적용한 뒤 문서 순서상 다음 제안으로 이동 |
| Tab | 제안 위가 아니거나 막힌 제안 위 | 적용하지 않고 다음 제안으로 이동 |
| Shift+Tab | 제안이 앞에 있음 | 이전 제안으로 이동 |
| Esc | 커서가 제안 위 | `현재 유지`(본문 변경 없음) 후 다음 제안으로 이동 |
| Esc | 사진·배치 메모 표시(문단 없음)에 포커스 | `현재 유지` 후 다음 제안으로. 뒤에 제안이 없으면 메모로 오기 전의 커서 위치로 돌아가고, 그 위치가 없으면 메모 앞(없으면 뒤) 편집 가능한 문단 끝에 커서를 둔다 |
| Tab / Shift+Tab / Esc | 앞(뒤)에 제안이 없거나 제안 위가 아님(Esc) | 가로채지 않고 브라우저 기본 동작. 포커스가 갇히지 않는다 |

- 한글 조합 중(`isComposing`, keyCode 229)에는 키를 무시한다. 편집이 잠겼거나 Alt/Ctrl/Cmd가 눌렸을 때도 무시한다.
- 회색 추천(2층, `✦ 추천 받기` / `Alt+\`)이 떠 있는 동안에는 그 추천이 키를 가진다. 그 문단의 인라인 diff는 비켜 있고 팝오버도 숨는다. 추천을 닫으면 다시 그려진다.
- 적용과 유지는 기존 `proposal-action` 계약(`{action, id, sig}`)을 그대로 쓴다. 대상 문구 검증·내용 지문(`sig`) 대조가 그대로 돌고, 호스트가 거절하면 아무것도 움직이지 않는다. 마크업이 아닌 이전 형식의 리뷰는 묶음 신선도 잠금을 유지한다.

### 편집 안전

- 제안 표시는 편집 중인 글에 영향을 주지 않는다. 직렬화·문단 글자 위치 계산·서식 적용·메모 위치 계산은 `ins`·`marker`를 건너뛴다. 한 문단 안 복사·끌기는 시작 직전에 그 문단의 표시를 걷어낸 뒤 브라우저 기본 복사를 쓰므로(서식 유지) 복사한 글에 섞이지 않고, 여러 문단에 걸친 복사는 복제본에서 `data-review-ui` 노드를 지운다.
- 표시를 걷어내고 다시 그릴 때 커서는 DOM 위치를 우선 그대로 두고, 바뀐 경우에만 글자 위치로 복원한다. 링크 글자 안의 커서는 링크 앞으로 튀지 않는다. 선택 방향도 지킨다. Shift+←로 뒤쪽으로 만든 선택은 다시 그린 뒤에도 기준점(anchor)이 오른쪽에 남는다(`setBaseAndExtent`).
- 표시가 있는 문단에서 서식을 적용할 때는 표시를 걷어낸 뒤에도 원래 선택 범위(DOM 위치)를 그대로 쓴다. 링크 글자 일부(예: `old cafe`의 `cafe`)를 골라 굵게 하면 그 글자만 굵어진다. 글자 위치로 다시 계산하면 링크 안의 위치가 링크 시작·끝으로 바뀌어 링크 전체가 굵어지거나 선택이 사라지므로, DOM 위치를 쓸 수 없을 때만 글자 위치로 대신한다.
- 회색 추천을 기다리는 동안 그 문단의 diff가 다시 그려져도(텍스트 노드가 나뉘어도) 결과를 버리지 않는다. 신선도 비교는 같은 서식의 이웃 조각을 합친 글자·서식 기준이라 노드가 어디서 나뉘었는지와 무관하다.
- 문단에 키 입력(편집 키), `beforeinput`, 한글 조합 시작, 잘라내기가 일어나면 그 문단의 제안 표시를 즉시 지우고(커서는 유지), 입력이 400ms 멈추면 다시 검증해 그린다. 조합 중에는 다시 그리지 않고 끝난 뒤에 그린다.
- 원고는 사용자가 적용하기 전에는 바뀌지 않는다. 검토 UI는 정본·저장 본문·미리보기·발행 결과에 들어가지 않는다.

### 화면 안내

- 오른쪽 패널과 상단 도움말은 인라인 표시 기준으로 고쳤다. 패널 문구는 "제안은 본문의 해당 구절에 바로 표시돼요(빨간 취소선은 삭제, 초록 밑줄은 추가) …"이고, 본문에 그려지는 제안 수는 `본문 변경됨` 제안을 제외하고 센다.

## 구절 채팅 — 2026-11-04

마크업 원고에서 구절을 드래그하면 뜨는 빠른 도구(`적갈색`·`노랑 형광펜`·`메모`·`✓ 체크`)에 **채팅에 추가**를 더했다. 고른 구절을 오른쪽 패널의 **구절 채팅**에 첨부하고 AI에게 묻는다(Cursor의 Add to Chat과 같은 흐름). 이전 형식에서는 버튼이 없고 서버도 거절한다.

- 첨부: 구절은 문단 ID와 함께 입력란 위 칩으로 붙는다. 같은 구절은 한 번만, 최대 5개(넘으면 오래된 것부터 빠짐)이며 `×`로 뗀다. 첨부하면 질문 입력란으로 포커스가 가고, 1080px 이하에서는 검토 패널이 열린다. 줄바꿈은 `\n`, 링크는 라벨 글자로 계산하며 diff·회색 추천 같은 리뷰 UI는 구절에 섞이지 않는다.
- 질문: Enter 보내기, Shift+Enter 줄바꿈, 한글 조합 중 Enter는 무시한다. 기다리는 동안 `취소`나 Esc로 요청을 끊는다. 구절을 첨부하지 않으면 선택한 묶음과 이웃 묶음을 맥락으로 쓴다. 대화 기록(최근 12턴)은 이 화면에만 있고 저장하지 않으며 `새 대화`로 비운다. 실패하면 질문과 첨부를 그대로 두어 다시 보낼 수 있다.
- 서버(`POST /api/blog/chat`)는 파일을 쓰지 않는다. 첨부 문단의 저장 전 원문을 받아 구절이 그 문단에 있는지 확인하고, 이웃 묶음 마크업·노트 `## 규칙`·검토 기준·제목·이웃 문단의 사람 메모(데이터)를 묶어 워크플로 서버의 [`chat-blog`](workflows.md#selection-chat-chat-blog--2026-11-04)를 동기로 호출한다. 구절이 바뀌었거나 문단이 없으면 400을 돌려준다. 자동 저장이 revision을 계속 바꾸므로 오래된 revision은 거부하지 않고 현재 파일을 읽는다.
- 답변: 짧은 답과 함께 고쳐 쓸 문장(최대 3개)을 `원문 → 제안` diff로 보여 준다. **본문에 반영**을 눌러야 원고가 바뀐다. 반영은 리뷰 제안 적용과 같은 `replaceInlineText` 경로로 그 문단의 최신 글에서 구절을 다시 찾고, 없거나 여러 번 있으면 막고 이유를 보여 준다. 반영 뒤에는 저장 전 변경으로 표시되고 ⌘/Ctrl+S로 저장한다. 해당 묶음과 이웃 묶음은 `변경 영향 있음`이 된다.
- **답변을 메모로 남기기**: 구절을 첨부한 질문의 답을 그 구절(첫 첨부)의 비공개 주석(`<원고>.annotations.json`, 오른쪽 `내 주석`)으로 저장한다(`Q. 질문\nA. 답변`). 구절이 이미 본문에서 바뀌었으면 저장하지 않고 알린다. 저장하면 본문의 메모 배지가 갱신된다.
- 워크플로 프로토콜이 3으로 올랐다. 이전에 띄운 워크플로 서버(기본 4318)는 다시 시작해야 하며, 그렇지 않으면 이전 버전 서버 안내가 보인다.

검증(2026-11-04, 합성 원고만, Homebrew Node 26): `typecheck`·`check:architecture`·`audit:public` 통과. `tests/unit/blog-chat.test.ts` 5개(결과 정리·프롬프트/크기 제한·저장 전 문단 사용·파일 무변경·오래된 구절/기준 거절·엔진 오류·이전 형식 거절·SDK 읽기 전용 설정) 포함 `npm test` 253/254 — 실패 1건(`face-mosaic`)은 worktree에 `native/editor-engine/.build/runtime/bin/ffmpeg`가 없어서 생긴 환경 문제다. 웹 Playwright(headless) `canonical-chat` 2개(드래그→첨부→질문→반영→저장, 사라진 구절 반영 거절, 후속 질문 기록, 메모 저장/거절, 390px 패널·가로 넘침 없음·엔진 오류 시 질문 유지)를 20회 반복해 40/40, `canonical-*`·`markup-layout` 전체 40/40 통과. 데스크톱 1440·모바일 390 스크린샷을 확인했다. 실제 SDK 응답 품질과 Electron spec은 이번에 확인하지 않았다.

## 사진 고르기 — 2026-11-04

상단 **사진 넣기**가 [전체 이미지 분석 구간](media-evidence.md)의 결과를 오른쪽 창으로 연다. 창은 모달이 아니어서 열어 둔 채 본문을 눌러 위치를 고른다.

1. 장면·태그·OCR·맥락을 검색하거나 촬영물로 좁힌다. 검색어는 공백으로 나눈 모든 단어가 맞아야 한다.
2. 사진을 눌러 설명·글자·태그·맥락·불확실성을 확인한다. 얼굴 후보가 있으면 자르거나 모자이크하라고 안내하며, 넣는 것을 막지는 않는다. 자르기·모자이크 기능은 이 창에 없다.
3. 대체 텍스트를 다듬고(분석 설명의 첫 문장이 시작값) 위치를 고른 뒤 **이 위치에 넣기**를 누른다. 위치는 스티커와 같은 문단·사진 사이 자리이며 본문을 누르면 그 뒤가 선택된다.
4. 본문에 `저장 전 사진`으로 표시되고 8초 동안 **빼기**로 취소할 수 있다. 유예가 끝나거나 ⌘S를 누르면 사진을 미디어 폴더에 복사하고 `<Photo>`를 원고에 쓴다. 저장 실패 시 배치는 화면에 남고 자동으로 다시 시도한다.

프로젝트 연결(`blog-projects.json`의 `config`, 또는 `npm run blog:editor` 설정)에 완료된 `results.json`의 절대 경로를 `mediaEvidence`로 넣는다. 없으면 창이 연결 방법을 안내한다. 열린 프로젝트의 연결을 바꾸면 앱을 다시 열어야 한다.

- 저장되는 파일 이름은 `<imageId>.<확장자>`다. 원고의 사진이 메타데이터 표의 행으로 바로 이어진다.
- 복사 전에 결과의 SHA-256과 대조한다. 바뀐 파일은 거절하고, 대상 이름에 다른 내용의 파일이 있으면 덮어쓰지 않는다. 같은 내용이면 재사용한다.
- `본문 사용`은 원고 사진과 바이트가 같은 이미지다. 이름이 달라도 찾지만, 잘라내거나 다시 인코딩한 사진은 찾지 못한다. 이미 쓴 사진은 다시 넣지 못한다.
- `status:resolved`이고 해시가 있는 jpg·jpeg·png·webp만 목록에 나온다. 나머지는 개수만 표시한다. 서버는 결과에 있는 ID의 이미지만 제공하고 절대 경로는 화면으로 보내지 않는다.
- 파일 복사가 끝난 뒤 원고 저장이 충돌로 실패하면 복사본이 미디어 폴더에 남을 수 있다. 다시 저장할 때 재사용한다.
- 목록 썸네일은 `sips`로 만든 400px 사본을 `results.json` 옆 `thumbnails/`에 캐시한다. 만들지 못하면 원본을 쓴다.
- 한 번에 30장까지 넣는다. 콜라주 구성, 넣은 사진의 삭제·이동, 사진 선택 판단의 자동 기록은 제공하지 않는다.

## 자동 저장·실시간 동기화 — 2026-11-05

마크업 원고는 입력을 멈추면 저절로 저장되고, 다른 도구가 `.md`를 바꿔도 화면이 저절로 따라간다. 저장 실패 때문에 글이 페이지에만 남거나 다시 불러와야 하는 상태를 없애는 것이 목적이다.

저장 (`src/features/canonical-blog/model/autosave.ts`)

- 마지막 변경 1.2초 뒤 저장한다. 문단을 벗어날 때와 창을 가릴 때는 바로, 페이지를 닫을 때는 `keepalive`로 저장한다. 저장은 한 번에 하나이고 그동안 바뀐 내용은 끝난 뒤 이어서 저장한다. 본문·제목·스티커·사진·삭제가 대상이다. ⌘S와 정본 저장 버튼은 즉시 저장이다.
- 저장 중에도 본문을 잠그지 않고 프레임도 다시 읽지 않는다. 캐럿·스크롤·되돌리기가 유지된다. 프레임 재로드는 레이아웃 스타일이 바뀔 때만 일어나며, 이때 저장 안 된 글은 화면에 다시 넣는다.
- 실패하면 편집을 유지하고 1초부터 30초까지 늘려 가며 자동 재시도한다. 상태는 `저장 전 변경`, `저장 중…`, `저장 완료`(파일 시각), `저장 실패 · 자동으로 다시 시도`로 표시한다.
- 삭제와 사진 배치는 8초 유예 뒤 저장한다(그동안 다른 편집은 계속 저장된다). 되돌릴 시간을 남기려는 선택이고, ⌘S·검토 요청·페이지 닫기는 유예를 건너뛴다. 이미 전송 중인 삭제는 취소할 수 없어 `삭제 취소`가 비활성화된다.
- 저장이 진행 중일 때 저장 전 글로 되돌려도 그 입력은 새 편집으로 남아 다음 저장이 이긴다. 대기 중인 사진·스티커의 자리는 저장으로 노드가 밀리면 바로 뒤 노드(`next`)를 기준으로 따라간다.
- 서버가 건너뛴 문단·사진·스티커 배치는 화면에 남고 상태는 `일부 저장 안 됨`으로 표시한다. 30초부터 5분까지 늘려 가며 자동 재시도하고 ⌘S는 바로 다시 시도한다. 닫으려 하면 경고한다(앱은 확인 대화상자). 서버가 거부한 묶음 삭제(마지막 묶음)는 되돌려 다시 표시한다.
- 빈 제목은 저장 대기가 아니라 `제목 비어 있음`으로 표시한다. 200자를 넘는 제목은 잘라 저장하고 알림으로 알린다.
- 페이지 닫기 저장이 64KB를 넘으면 `keepalive`로 보낼 수 없어, 닫기 전에 경고하고 일반 저장을 시작한다.

입력 때문에 실패하지 않게 (`src/shared/blog-markup-edit.ts`)

- 문단 안의 빈 줄은 문단 나눔이다. 첫 조각은 ID를 유지하고 나머지는 새 `P{n}`을 받으며 서식은 줄을 따라간다. 프레임은 입력 중인 DOM을 같은 자리에서 나누고 캐럿은 그 글자를 따라간다. 조합 중이면 조합이 끝난 뒤 나눈다. 끝의 빈 줄은 나눔이 아니라 버린다.
- 원고 문법과 겹치는 글자는 한 글자씩 비슷한 글자로 바꿔 저장한다: `<` `>` → `＜` `＞`, `⟦` `⟧` → `〚` `〛`, `**` → `＊＊`, `==` → `＝＝`. `¶ id`나 각주처럼 보이는 줄은 앞 공백을 줄바꿈 없는 공백으로 바꾼다. 입력 중인 문단은 포커스를 벗어날 때 바뀐 글자로 표시된다. 이 치환은 자기 저장이므로 충돌로 처리하지 않는다.
- 내용을 모두 지운 문단은 빈 문단으로 저장한다. 빈 제목은 보내지 않는다.
- 한 문단이 파싱·검사에서 막히면 그 문단만 화면에 남기고 다른 변경은 저장한다. 사진·스티커·삭제도 마찬가지이며 결과는 응답의 `skipped`로 알린다. 파일에 이미 있던 검사 오류는 사용자의 저장을 막지 않으며, 문단이 나뉘어 새 ID로 옮겨간 오류도 기존 오류로 본다. 새 조각에서 새로 생긴 오류는 원래 문단의 편집만 보류한다.
- 같은 저장이 두 번 도착해도(페이지 닫기, 응답 유실 뒤 재시도) 나눈 문단이 중복되지 않는다. 새 ID는 `revision+문단`으로 메모리에 기억하고, 재시작 뒤에는 파일에서 같은 글이 바로 뒤에 있는 새 문단을 찾아 재사용한다. 사진도 배치 ID로 한 번만 넣는다(메모리 기준이라 재시작 뒤 사진 재전송은 막지 못한다).

외부 변경과 병합 (`MarkupStore.save`, `src/shared/blog-markup-store.ts`)

- 기존 1.5초 `review-status` 폴링이 현재 revision을 함께 돌려준다(`fs.watch`와 이벤트 스트림은 쓰지 않아 지연은 최대 약 1.5초다). 달라졌고 로컬 변경이 없으면 문서를 받아 제자리에서 갱신하고, 로컬 변경이 있으면 저장을 당겨 서버가 3-way 병합한다.
- 프레임은 렌더된 article을 받아 키가 같은 노드를 남기고 바뀐 곳만 고친다. 포커스가 있거나 저장 안 된 문단은 건드리지 않고, 포커스 문단의 새 글은 포커스가 떠날 때 적용한다. 그 전에 입력하면 그 입력의 기준은 예전 글로 전달된다. 프레임의 변경에는 번호가 붙고 sync가 호스트가 본 번호를 함께 보내, sync와 엇갈린 입력은 저장 안 된 글로 보호된다. 포커스 문단이 파일에서 지워지면 포커스가 떠날 때 사라지고, 그 전에 입력하면 이전 문단 뒤에 되살린다.
- 파일이 앞으로 가도 남아 있는 편집은 자기가 시작한 글을 기준(`base`, 제목은 `titleBase`)으로 보낸다. 서버는 그 기준과 현재 글을 문단 안에서 줄 단위로 병합하므로 다른 줄의 외부 수정이 조용히 되돌아가지 않는다. 같은 줄이면 충돌이다. 저장 응답의 `written`은 병합 전 이 저장이 이해한 글이라 이후 입력의 기준이 된다.
- 기준은 메모리, 페이지가 보낸 `baseText`, `.history`의 순서로 복구한다. 모두 없으면 현재 파일에 바로 반영하고 경고를 남긴다. 그래서 재시작이나 외부 변경 뒤에도 기준 만료로 실패하지 않는다. 추천·채팅·검토 요청도 오래된 revision을 거부하지 않는다.
- 줄 병합이 안 되면 현재 파일 위에 패치를 다시 적용한다. 같은 문단을 양쪽이 고쳤으면 쓰던 글을 남기고, 덮인 판은 `.history/<파일>/conflict-*.md`에 따로 보관(최근 30개, 일반 회전과 별개)하며, 화면에 닫을 수 있는 작은 알림만 띄운다. 외부에서 지워진 문단을 고치던 중이면 그 자리에 되살린다. 외부에서 고친 문단·묶음을 지운 경우는 삭제를 유지하고 충돌(`kind:"delete"`)로 알린다. 이후 저장은 막히지 않는다. 알림은 머리·도구 영역 바로 아래에 고정된다.
- 다른 도구의 `.lock`은 서버가 3초 동안 기다린 뒤 `BUSY`로 돌려주고 페이지가 재시도한다. 120초 넘은 잠금은 비정상 종료로 보고 인수한다. 에이전트 저장의 `TEXT_GUARD` 규칙은 그대로다.
- 일반 기록은 자동 저장이 잦아도 60초에 한 번만 남기고 60개까지 보관한다. 도구가 쓰지 않은 외부 판은 언제나 남긴다.

알려진 한계

- 문단이 나뉜 직후의 ⌘Z는 나누기 전 상태로 정확히 돌아간다고 보장하지 않는다(스크립트가 DOM을 바꿨기 때문).
- 사진·스티커의 자리를 정하던 바로 뒤 노드가 사라지면 같은 번호, 없으면 묶음 끝으로 옮긴다.
- `keepalive` 저장은 본문 64KB 제한 때문에 `baseText`를 보내지 않고 서버 메모리·`.history`의 기준을 쓴다.
- 응답을 잃은 저장 직후 사용자가 저장 전 글로 되돌리면 서버는 변경 없음으로 판단해 파일의 글이 남는다. 로컬 서버에서 응답 유실과 되돌리기가 겹칠 때만 생긴다.
- 분할이 전달된 뒤 문단의 첫 조각이 없어지거나 나뉜 조각 수가 줄어든 재전송은 이전 조각을 지우지 않는다.
- 옛 레이어 형식(`format` 없음)은 범위 밖이라 수동 저장·다시 불러오기를 유지한다.

## 블로그 탭 내장 — 2026-11-11

**별도 창이던 이유.** 처음 데스크톱에 붙일 때(`043b463`, [마크업 편집기 연결](markup-editor-integration.md)의 "loopback editor server and an isolated editor window") 원고 페이지를 대시보드 브리지에서 떼어 놓으려고 프로젝트마다 `BrowserWindow`(partition `canonical-editor`, sandbox, preload 없음)를 열었다. 서버 CSP `frame-ancestors 'self'`와 cross-site 요청 403도 같은 의도다. 창이어야 하는 기능상 이유는 없었다. 사용자 결정으로 메인 창 블로그 탭 안의 탭으로 바꿨다.

**구조.**

- `blog:openCanonical`은 창을 만들지 않는다. 프로젝트 서버(`127.0.0.1:<임의 포트>`)를 띄우거나 재사용하고 `{projectId,title,url}`만 돌려준다. 연결이 바뀐 프로젝트는 그 탭이 열려 있는 동안 "프로젝트 연결이 변경됐어요…" 오류로 거부한다. 탭을 모두 닫은 뒤 다시 열면 새 연결로 연다.
- `BlogWorkspace` 위쪽 탭 줄에 **프로젝트 / 원고·배치 / 레퍼런스 추출·탐색** 뒤로 연 프로젝트의 탭(제목 = 프로젝트명, `×` = 탭 닫기)이 붙는다. 같은 프로젝트를 다시 열면 그 탭을 고른다.
- 에디터는 `iframe.blog-editor-frame`이다. 탭을 닫기 전까지 언마운트하지 않고 `hidden`만 바꾼다. 다른 탭·메뉴로 갔다 와도 페이지가 다시 로드되지 않아 저장 전 편집이 남는다.
- 높이는 창 아래쪽까지 채운다(`100vh - 탭 줄 위치 - 여유`). 개발모드 터미널 패널이 열리면 `styles.css`의 `.compact-shell[data-terminal]` 규칙(다른 화면의 하단 여백과 같은 자리)이 여유를 패널 최대 높이 `min(70vh, 760px)`(접힘 90px)만큼 늘려 에디터 아래쪽이 패널에 가리지 않는다.
- 탭 닫기는 `blog:closeCanonical`에 먼저 묻는다. 닫기가 허용되고 그 프로젝트의 frame이 하나도 남지 않으면 3초 뒤 서버를 닫고 목록에서 지운다. 3초는 지운 페이지의 `pagehide` keepalive 저장이 서버에 닿을 시간이고, 그 사이 다시 열면 취소한다. 남은 서버는 앱 종료 때 `dispose`로 닫는다.

**격리 경계.**

- iframe에는 preload·브리지가 없다. 메인 창은 `nodeIntegrationInSubFrames`를 쓰지 않아 subframe에 preload·`ipcRenderer`가 없고, main의 IPC 검사(`trustedIpcSender`)는 메인 창 mainFrame만 받는다. 에디터 frame을 sender로 넣은 호출은 `Untrusted IPC sender`다.
- 대시보드(`file://`)와 에디터(`http://127.0.0.1:<port>`)는 서로 다른 origin이라 서로의 DOM에 닿지 않는다.
- iframe `sandbox="allow-scripts allow-same-origin allow-forms allow-modals allow-popups"`. 각 토큰의 쓰임: 에디터 실행, same-origin 원고 frame·API 호출, 구절 메모·채팅 `<form>`, `confirm()`과 beforeunload, 스티커 도움말 링크(`target=_blank`). `allow-top-navigation`이 없어 에디터가 대시보드를 이동시키지 못한다. `allow` 속성으로 권한을 위임하지 않는다.
- CSP는 데스크톱이 띄운 서버에만 완화한다(`startCanonicalEditor`의 `desktopFrame`). 에디터 페이지와 원고 frame이 `frame-ancestors 'self' file:`을 보낸다. Electron 45 실험에서 `file:` 부모를 허용한 값은 이것뿐이었다(`'self'`, `'self' file://`, 정확한 `file:///…/index.html`, `*`은 모두 `ERR_BLOCKED_BY_RESPONSE`). 대시보드 렌더러는 패키징·개발 모두 `dist/index.html`을 `file://`로 띄우고 Vite dev 서버는 쓰지 않는다.
- cross-site 403 예외는 `GET /?blogEditor=1`에 `Sec-Fetch-Dest: iframe`, `Sec-Fetch-Mode: navigate`일 때 하나다(부모가 `file://`라 iframe 문서 요청이 cross-site로 온다). 다른 cross-site 요청, POST, `Origin` 검사는 그대로다. `npm run blog:editor`는 이전 정책(403, `'self'`, 에디터 페이지 CSP 없음)을 유지한다.
- 메인 창 핸들러가 이전 에디터 창 설정을 대신한다. 새 창은 도움말 URL만 외부 브라우저로 열고 모두 거부한다. 에디터 frame에 포커스가 있거나 referrer가 에디터 origin이면 에디터 요청으로 본다. `will-frame-navigate`는 에디터 frame이 자기 서버 origin 밖으로 가는 이동을 막는다. 권한 요청은 세션 전체에서 거부하고, 권한 확인은 에디터 origin일 때 거부한다.

**미저장 경고.** iframe을 지우면 beforeunload가 돌지 않고, 실제 beforeunload 대화상자는 frame 안에서 사용자 입력이 있어야 뜬다. 그래서 main이 에디터 frame에서 취소 가능한 `beforeunload` 이벤트를 보내 페이지 자신의 판정(`live`면 저장 실패·보류·keepalive 초과, 아니면 `dirty`)을 읽는다. 실행이 실패하거나 2초 안에 답하지 않은 frame은 미저장으로 본다.

- 에디터에 저장 안 된 변경이 있으면 이전 창과 같은 대화상자("아직 파일에 저장되지 않은 변경이 있어요." / 그래도 닫기·계속 편집)를 띄운다. 탭 닫기, 메인 창 닫기, 앱 종료(⌘Q)에서 묻는다.
- 창 닫기·종료에서는 대시보드 페이지도 같이 묻는다(원고·배치 초안, 경험 입력 폼의 guard). 에디터는 깨끗하고 그쪽만 미저장이면 일반 문구("저장하지 않은 변경이 있어요." / "닫으면 저장하지 않은 내용이 사라질 수 있어요.")를 쓴다. 에디터 탭이 없을 때 실제 beforeunload가 부르는 `will-prevent-unload`도 일반 문구다.
- "그래도 닫기"는 그 한 번의 닫기·종료 시도에만 유효하다. 진행 중 작업·AI 작업 확인·`will-prevent-unload`의 "계속 편집"으로 시도가 취소되면 바로 지우고, 5초가 지나도 사라진다. 종료 정리가 시작된 뒤의 `will-prevent-unload`는 통과시킨다.
- background QA는 대화상자 없이 통과한다. QA 전용 `REELS_QA_STUBBED_DIALOGS=1`이면 background QA에서도 대화상자 분기를 타며, spec이 `dialog.showMessageBoxSync`를 스텁해 창을 보이지 않고 두 선택을 검사한다.
- 탭을 닫으면 페이지의 `pagehide` keepalive 저장이 그대로 돈다.

**단축키.** ⌘S 등 에디터 단축키는 frame 안 keydown으로 그대로 동작한다. 개발모드 host 단축키(⌘N/T/W/1–9)는 메인 창 `before-input-event`가 받아 키보드가 에디터 안에 있어도 패널로 간다.

**정리한 것.** 에디터 창에 터미널을 붙이려던 코드(`workbench-preload.ts`, `BlogEditorShell.tsx`·CSS, 에디터 창 신뢰 확장, `editorWindows`·`emitWorkbench`·`handleFrom`, 빌드 엔트리, `editor-workbench.spec.ts`, development-workspace 문서 절)를 지웠다. `ipc-trust.ts`는 메인 창 판정만, `workbench-bridge.ts`는 메인 preload용으로 남겼다. `?blogEditor` 진입은 `CanonicalBlogEditor`만 그린다.

**제한.**

- 새 창 요청은 어느 frame이 보냈는지 Electron이 알려 주지 않는다. 에디터 스크립트가 대시보드에 포커스가 있을 때 `noreferrer`로 연 http(s) 주소는 대시보드 규칙(외부 브라우저 열기)을 탄다. 에디터는 앱이 내보내는 스크립트만 실행하는 전제다.
- 저장소가 partition `canonical-editor`에서 메인 창 기본 세션으로 바뀌었다. 에디터는 쿠키·localStorage를 쓰지 않아 옮길 데이터는 없다.
- 대화상자 선택은 스텁으로만 검증했다. "그래도 닫기" 뒤 진행 중 작업·AI 작업 확인으로 취소되는 경로는 Electron에서 재현하지 않았고 코드로만 리셋한다. 프로브 실행 실패(거부)를 미저장으로 보는 분기도 자동 검증하지 못했다.

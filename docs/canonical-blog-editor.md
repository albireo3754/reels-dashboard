# 정본 스마트 에디터

마크업 정본은 [마크업 편집기 연결](markup-editor-integration.md)을 따른다. 대시보드의 정본 스마트 에디터 열기 버튼이 앱 내부 창과 loopback 서버를 직접 연다. 아래 인라인 본문/레이어 JSON·4320 설명은 이전 형식 전용이다.

사용자는 이미 만든 정본의 사진·콜라주·문단·강조를 실제 배치로 보면서 본문을 직접 고친다. 별도 `BlogDraft` 복사본이나 검토 파일 업로드 화면을 정본 편집기로 취급하지 않는다.

## 실행과 화면

`npm run build` 후 `npm run blog:editor -- /absolute/path/to/private-config.json`을 실행한다. 설정은 콘텐츠 작업공간 또는 개인 임시 폴더에 두며 앱 소스에 개인 경로·원고를 복제하지 않는다.

```json
{
  "canon": "/absolute/content/article.md",
  "layers": "/absolute/workspace/layers",
  "layout": "/absolute/workspace/publishing/smarteditor-draft-layout.html",
  "media": "/absolute/content/media",
  "port": 4320
}
```

`http://127.0.0.1:4320/?blogEditor=1`에서 실제 정본을 연다. 앱의 블로그 화면에도 이 로컬 편집기로 가는 링크가 있다. 서버는 설정으로 지정한 정본 1개만 편집한다. 기존 4318 워크플로 서버나 실행 중인 Electron 앱을 재시작하지 않는다.

- 왼쪽: 기존 묶음 경계·이름으로 이동.
- 가운데: 기존 미리보기 CSS·글꼴, 사진·콜라주, 문단·부분 강조. 문단을 클릭해 직접 수정하고 구절 선택 후 굵게·글자색·배경·서식 제거. Enter는 같은 문단 내 줄바꿈이다.
- 오른쪽(보조): 선택 묶음의 검토 요약, 실행 상태, 화면 검토, 제안 목록(상태·이유·`본문에서 보기`). 적용·현재 유지 판단은 본문 대상 문구 옆 제안 카드에서 한다([본문 내 제안 검토](#본문-내-제안-검토--2026-11-02)). 선택 이력은 현재 화면에만 보관되며 본문 변경은 저장해야 정본에 남는다.
- 상단: 정본 저장, 최신 정본 다시 불러오기, 모바일/PC 폭, 이 묶음/변경분 검토. 편집이나 시간 경과는 평가를 실행하지 않는다.

현재 지원 편집 범위는 기존 제목·문단의 문장·줄바꿈·부분 강조다. 사진과 묶음 배치는 기존 레이어를 그대로 표시하며, 이 화면에서 사진 추가/삭제·콜라주 재구성·새 문단/묶음 생성은 아직 제공하지 않는다. 기존 묶음 통째 삭제는 [묶음 삭제·저장 단축키](#묶음-삭제저장-단축키--2026-11-03)를 따른다. 네이버 장소 지도·블로그씨 카드는 기존 자리 표시다.

## 저장 계약

정본의 `### 본문`에서 문단 ID T1…을 기존 grouping/bundle 레이어와 대조한다. 문단 매핑 불일치·누락/겹침·다른 세션의 변경은 저장을 거절한다. `### 제목`과 변경한 본문 문단만 수정하고 frontmatter·사진 지시문·비공개 메모·나머지 문단은 보존한다. 해당 문단의 `emphasis-layer.json`과 미리보기 HTML을 함께 갱신하며 `layers/editor-backups/`에 원본을 남긴다. 새 독립 초안은 생성하지 않는다.

입력 revision은 정본·묶음·블록 순서·강조 파일의 지문이다. 저장 직전 다시 대조하고 각 파일 교체 직전 외부 변경을 확인한다. 실패 시 자신이 쓴 내용만 복구한다. 여러 파일의 교체 전체가 파일시스템 단일 원자 연산인 것은 아니므로 프로세스 강제 종료 후에는 백업과 실제 파일 상태를 확인한다. 기존 엔진의 compose.py·pipeline-state.json·리뷰 산출물을 UI에서 임의 실행/갱신하지 않는다. 텍스트 레이어와 엔진 상태는 엔진 다음 실행에서 갱신한다.

## 명시적 검토 요청과 엔진 경계

검토 버튼은 편집 내용이 있으면 정본 저장 성공 후 `layers/editor-requests/<uuid>.json`을 만든다. 실패한 저장으로는 요청을 만들지 않는다. 요청에는 `kind:blog.editor.review-request`, `status:pending`, `trigger:user`, `basedOn` 정본 revision, `bundleIds`, 정본/레이어 경로와 시간이 들어 있다. 변경분은 해당 묶음과 이웃 전환을 포함한다. 실제 재시작 단계 결정·에이전트 실행·새 리뷰 생성은 별도 엔진이 맡는다. 현재 소비자가 연결되지 않았으므로 UI는 **엔진 처리 대기**로 표시하며 평가 완료를 가장하지 않는다. 사용자가 JSON을 수동으로 옮길 필요는 없다.

기존 리뷰의 textHash는 Python 합성기의 텍스트 해시와 대조한다. 이것만으로 사진/서식까지 최신이라고 주장하지 않는다. 새 엔진의 전체 묶음 fingerprint 계약과 요청 소비·상태 갱신 연결은 후속 작업이다.

## 확인

합성 콘텐츠를 사용하는 테스트에서 실제 파일 저장·강조 반영·미리보기 반영·비공개 메모/사진/다른 문단 보존·동시 수정 차단·명시적 검토 큐 생성을 검사한다. 브라우저에서는 contenteditable 입력과 실제 선택 구절 서식 변경, 저장/새로고침, 모바일 폭, 충돌 후 사용자 변경 보존을 확인한다. 실제 콘텐츠는 읽기 및 개인 임시 복사본 검증만 하며 검증용 문장을 정본에 저장하지 않는다.


## Codex SDK 문안 검토

정본 저장 후 **Codex로 선택 묶음 검토**를 누르면 공통 [워크플로 서버](workflows.md#codex-sdk-execution--2026-11-01)가 저장된 로그인으로 SDK를 실행한다. 데스크톱 앱에서는 앱이 [워크플로 서버를 내장](workflows.md#desktop-embedded-server--2026-11-03)하므로 따로 실행하지 않는다. 독립 실행 편집기(`npm run blog:editor`)는 워크플로 서버를 함께 실행해야 한다. 편집기 서버는 같은 origin의 요청을 전달한다. 기존 엔진 작업 폴더에 남기는 검토 요청과 별개의 명시 실행 경로다.

결과는 제안으로 표시하고 자동 반영하지 않는다. 요청 후 정본 revision이나 저장 전 편집이 바뀌면 적용을 막는다. **SDK 제안 적용**은 화면에 반영하고 **정본 저장**은 기존 저장·백업 검증을 수행한다. 이번 SDK 검토는 전달된 문안·기준에 한정되며 사진·완성 화면을 검토했다고 주장하지 않는다.

## 디자인·서식 보강 — 2026-11-01

1080px 이하에서는 검토를 원고 맨 아래에 놓지 않고 **검토 보기**로 여는 패널로 표시한다. 닫기·바깥 영역·Escape로 닫으며 키보드 포커스는 패널 안에서 이동하고 닫으면 원래 버튼으로 돌아간다. 모바일 묶음 목록은 **글의 흐름**으로 펼친다. 상단 도구 높이를 측정해 본문 이동·고정 패널 위치에 사용한다.

본문의 구절을 선택하면 현재 글자 크기·굵기·색이 도구에 표시된다. 글자 크기는 기존 공통 SmartEditor 단계(11–45px), 글자색은 기본/적갈/갈색/하늘/초록 및 직접 색 선택, 배경색은 노랑/살구/연회색 및 직접 선택을 지원한다. **배경색만 지우기**와 **서식 지우기**를 구분한다. 팔레트·크기 메뉴로 포커스가 옮겨져도 원래 구절에 적용하며, 크기 변경이 기존 색·굵기·배경을 제거하지 않는다. 제목 서식과 문단 정렬·글꼴 교체는 이 추가 범위가 아니다.

기존 강조 제안은 **현재 서식 / 제안 서식**을 구절·크기·색·배경·굵기로 비교한다. 본문의 실제 글꼴 파일과 문단의 기본 크기를 재사용하고, 제안 이유와 묶음 평가 요약은 펼쳐 읽는다. 글자 스타일은 정본·강조 레이어 저장에 포함되며 검토 버튼을 누르지 않은 편집은 평가를 실행하지 않는다.

검증: 선택→색상→24px→굵게→배경만 제거→정본 저장/재열기, 서식 전후 표시, 1024px 검토 패널·Escape/포커스 복귀, 390px 묶음 접기/가로 넘침, 기존 정본 저장 충돌 보호 및 SDK 명시적 적용 회귀를 합성 콘텐츠로 확인했다. 실제 원고는 화면 검수만 한다.

기존 미디어가 심볼릭 링크인 경우 서버 설정의 `assetFiles`에 실제 원본 파일 경로를 개별 등록할 수 있다. 등록된 블록 이름과 등록된 원본 대상이 모두 일치할 때만 제공하며, 다른 대상으로 바뀐 링크는 거절한다. 이번 실제 화면 검수에서 콜라주 사진 2장의 기존 원본 링크를 이 방식으로 연결했다. 원본 이동·복제·이미지 편집은 하지 않았다.

## 외부 실행기 묶음 리뷰 — 2026-11-02

앱 안의 Codex SDK 대신 Claude Code Workflow나 Codex 서브에이전트가 같은 묶음 리뷰 계약을 실행할 수 있다. 바뀌는 것은 실행 주체뿐이다. 입력(`reviewMaterials`: 범례 + 노트 `## 규칙` + 원고, `reviewGuidance`, 사용자 주석), 결과 검증(`validateMarkupReview`), 저장(`storeMarkupReviews`가 요청한 묶음만 교체), 신선도 판정은 앱과 같다. 실행 절차와 역할 지침은 콘텐츠 작업공간의 리뷰 루프 스킬에서 관리한다.

```sh
node --import tsx scripts/blog-review.ts projects
node --import tsx scripts/blog-review.ts status <project-id>
node --import tsx scripts/blog-review.ts prepare <project-id> <new-packet-dir> [--changed | --all | --bundles B1,B2]
node --import tsx scripts/blog-review.ts import <project-id> <packet.json> <result.json> --provider <name> [--run <id>]
```

- 프로젝트는 `blog-projects.json`에 등록된 ID로 고른다. `REELS_DASHBOARD_USER_DATA`로 user-data 위치를 바꿀 수 있다. markup 형식이고 `review` 경로가 있는 프로젝트만 지원한다.
- `prepare`는 새 패킷 폴더에 `packet.json`(앱 요청과 같은 `markupReviewInput`과 묶음 해시), `source.md`, `guidance.md`, `bundles/<ID>.json`(앞뒤 묶음 원문, 허용 문단 ID, 기존 강조 구절, 해당 주석, 문단 ID enum을 넣은 결과 스키마)을 만들고, 빈 `out/` 폴더도 만든다. 기본값 `--changed`는 검토가 없거나 텍스트가 바뀐 묶음만 고른다. 공개 저장소 안의 경로는 거부한다. 같은 폴더를 두 번 쓰지 않는다.
- `import`는 패킷과 원고가 같은지 확인하고, 앱과 같은 검증을 거쳐 `review` 파일에 저장한다. `requests/<id>.json`에 완료 영수증(`provider`, `runId` 포함)을 남기며, 이 영수증은 앱 worker가 다시 처리하지 않는다. 같은 패킷은 한 번만 가져온다. 검토 중 원고가 바뀌면 `stale`로 기록한다. 원고 파일은 수정하지 않는다.
- 외부 실행기에는 화면 캡처가 없다. `visual.status`가 `unverified`가 아니면 가져오기를 거부하므로, 이 경로의 결과는 `passed`가 될 수 없다. 화면 판정은 기존 앱 검토(360/390/430px 캡처)로 따로 받는다.
- `status`는 묶음별 판정, 실행 주체, 텍스트·화면 신선도, 남은 제안 수(필수/권장/관찰), 다시 검토가 필요한지를 반환한다.

검증: 합성 원고로 패킷 생성, 공개 저장소 경로 거부, 화면 통과 주장 거부, 가져오기 후 에디터 검토 목록 표시, 중복 가져오기 거부, 원고 무변경, 원고 변경 뒤 재검토 대상 선택을 확인했다(`tests/unit/blog-external-review.test.ts`). 기존 worker 저장 로직을 공용 함수로 옮긴 뒤 worker 테스트도 통과했다.

## 본문 내 제안 검토 — 2026-11-02

- 텍스트 제안은 대상 문구 위치에 바뀌는 부분만 표시한다(삭제는 취소선·붉은 배경, 삽입은 카드의 diff). 문단을 복제하지 않는다. 서식 제안은 문단 글꼴·크기에 각 run의 색·배경·굵기·크기를 입힌 현재/제안 샘플을 문구 근처에 나란히 보여 준다.
- 각 카드에 `적용`·`현재 유지`·`이유`가 있다. 적용은 기존 적용 경로(대상 문구 검증·오래된 제안 잠금·동시 편집 보호)를 다시 거쳐 편집 내용에 들어가고, 저장·백업은 기존과 같다. 현재 유지는 본문을 바꾸지 않는다. 결정한 카드는 사라진다.
- 적용이나 직접 편집 뒤 같은 문단의 나머지·겹치는 제안을 다시 검증한다. 대상이 바뀌었거나 위치를 하나로 찾지 못하면 본문에 표시하지 않거나 잠긴 카드로 이유만 보여 주고 적용을 막는다.
- 사진·배치 의견처럼 문장 치환이 아닌 제안은 해당 묶음(언급된 사진이 있으면 그 사진) 근처에 의견 카드로 둔다.
- 검토 UI는 리뷰 전용이다. 본문 표시는 CSS Custom Highlight와 `[data-tid]` 문단 밖 형제 카드로만 그리며, 편집기 iframe에 `proposals` 메시지가 올 때만 생긴다. 정본·저장 본문·파생 미리보기·발행 결과·화면 캡처 창에는 섞이지 않는다.
- 모바일에서는 카드가 대상 문단 바로 아래에 종이 폭 안에서 줄바꿈되며 가로 스크롤을 만들지 않는다.
- 링크는 본문에 라벨만 보이므로, 대상이 링크 주소나 링크 글자 일부에 걸친 제안은 위치를 표시하지 않고 잠근다. 링크 전체를 포함하는 제안은 링크 라벨 전체를 대상으로 표시한다.
- 적용·현재 유지 클릭은 화면에 표시했던 제안의 내용 지문을 함께 보낸다. 재검토로 같은 ID의 제안 내용이 바뀌었으면 그 클릭을 거부하고 다시 확인하도록 안내한다.
- 키보드로 결정하면 포커스가 다음 제안 카드로 이동한다. 펼쳐 둔 `이유`는 편집 중 다시 그려도 유지된다. `이유`와 패널의 `제안 이유`에는 잘리지 않은 원문·제안 전문이 있다.

검증 (2026-11-02, 합성 원고만 사용): `typecheck`, `check:architecture`, `audit:public`(551 entries)가 통과했다. Homebrew Node 26 기준 `npm test` 197/197이 통과했고, 그중 `inline-review` 단위 테스트는 18개다. 브라우저 검증은 headless로 `canonical-inline-review`(2개), `canonical-blog`, `canonical-formatting`, `canonical-save-status`(2개), `canonical-sdk`, `markup-layout`을 실행해 8/8 통과했다. `canonical-inline-review`와 `canonical-save-status`를 3회 반복해 12/12 통과했다. `npm run build` 뒤 Electron background QA(`markup-editor`, `blog-scroll`)는 4개 통과, 2개 skip이다. skip한 것은 실제 원고 확인과 live visual review로, `REELS_MARKUP_CONFIG`가 필요해 실행하지 않았다. 확인한 항목은 본문 diff 표시, 적용과 현재 유지, 한 문단의 여러 제안 재검증, 대상 변경 뒤 적용 차단, 링크 내부 대상 차단, 재검토 뒤 오래된 클릭 거부, 키보드 포커스 이동, `이유` 펼침 유지, 저장 뒤 다시 열었을 때 원고에 리뷰 UI가 없는지다. Playwright 웹 spec은 Node 22(nvm)로 실행하면 `canonical-sdk`가 OpenTelemetry 로드 오류로 수집되지 않는다. 이 오류는 이번 변경과 관계없다.

## Tab 추천 — 2026-11-03

마크업 정본 편집기에 Cursor식 키보드 추천을 더했다. 두 층으로 나뉘며, 둘 다 사용자가 키를 누르기 전에는 본문을 바꾸지 않는다.

### 1층: 검토 제안을 Tab으로 넘기기

- 새 검토 경로는 없다. [본문 내 제안 검토](#본문-내-제안-검토--2026-11-02)의 제안 가운데 현재 문단에 위치가 확정된 제안(적용 가능)만 대상이다.
- 커서가 그런 제안이 있는 문단에 있으면 대상 아래에 작은 안내 상자(`role=status`, `aria-live=polite`)가 뜬다. 바뀌는 부분만 보여 주는 짧은 diff와 `Tab 적용 · Esc 유지 · Shift+Tab 이전`, 그리고 그 묶음을 다시 검토하는 `다시 검토` 버튼이 있다. 안내 상자는 종이 폭 안에 머문다. 커서 위치를 포함하는 제안이 우선이고, 없으면 같은 문단에서 커서 뒤의 가장 가까운 제안을 고른다.
- **Tab**: 커서가 제안 위(또는 바로 옆)에 있으면 적용한다. 적용 경로는 카드의 `적용`과 같아서 대상 문구 검증, 오래된 제안 잠금, 내용 지문 대조를 그대로 거친다. 적용한 뒤 문서 순서상 다음 제안의 시작 위치로 커서를 옮긴다. 다음 위치는 갱신된 제안 목록으로 다시 계산하며 이전 offset을 그대로 쓰지 않는다. 커서가 제안 위에 있지 않으면 첫 Tab은 적용하지 않고 다음 제안으로 이동만 한다.
- **Shift+Tab**: 이전 제안으로 이동한다. **Esc**: 커서가 제안 범위 안에 있을 때만 그 제안을 `현재 유지`로 처리하고(본문 변경 없음) 다음으로 이동한다. 커서 뒤의 제안이 안내 상자에 보이기만 하는 상태에서는 Esc를 가로채지 않는다. 보이기만 하는 제안이 실수로 숨겨지지 않게 하려는 것이다.
- 안내 상자는 활성 제안이 없으면 DOM에서 지운다. 안내 문구는 계속 남는 별도 live region(`data-review-ui="live"`)으로도 읽어 준다. 대상이 화면 밖이면 그만큼만 스크롤한다.
- 링크 일부를 겨냥한 제안처럼 잠긴 제안은 이동 대상에서 빠진다. 해당 카드에는 기존처럼 이유가 표시된다.
- 앞이나 뒤에 남은 제안이 없으면 Tab·Shift+Tab·Esc를 가로채지 않으므로 포커스가 갇히지 않는다. 한글 조합 중(`isComposing`, keyCode 229)이거나 편집이 잠겼을 때는 키를 무시한다.

### 2층: 직접 요청하는 회색 추천

- 타이핑만으로는 요청하지 않는다. 상단의 **✦ 추천 받기** 버튼이나 본문 안의 **⌥\\**(Alt+Backslash)로 요청할 때만 커서 위치에 이어 쓸 문장을 받는다. 마크업 정본에서만 쓸 수 있고, 이전 형식에서는 버튼이 비활성이며 이유를 툴팁으로 알려 준다.
- 기다리는 동안 버튼은 회전 아이콘과 `추천 중… (Esc 취소)`로 바뀌고, 본문 커서 자리에 작은 회전 표시(`추천을 기다리는 중`)가 나타난다. 일부러 기다리게 하는 흐름이다. Esc나 새 요청은 진행 중인 요청을 취소한다.
- 응답을 기다리는 사이 문단 내용, 커서 위치, 선택 범위(시작 위치·선택 여부), 포커스, 문서 revision 중 하나라도 바뀌면 결과를 버리고 `본문이 바뀌어 추천을 버렸어요. 다시 요청해주세요.`를 보여 준다. 추천이 비어 있으면 `이 위치에 추천할 문장이 없어요.`를 보여 준다.
  - 포커스는 응답 시점의 실제 포커스로 판단한다. 기다리는 동안 포커스가 문단 밖(프레임 안의 다른 버튼·메모 배지 등)으로 가면 바로 취소하고, 늦게 온 응답이 포커스를 문단으로 되돌리지 않는다. 다른 앱으로 전환하는 것만으로는 취소하지 않는다.
  - 커서 끝이 같아도 Shift+방향키 등으로 선택을 만들었다면 결과를 버리고, 만든 선택은 그대로 둔다.
  - 링크는 본문에 라벨만 보여서 라벨 안의 모든 위치가 링크 시작 위치 하나로 계산된다. 그래서 커서가 링크 글자 안에 있으면 요청하지 않고 `링크 글자 안에서는 추천할 수 없어요. 링크 앞이나 뒤에 커서를 두고 다시 요청해주세요.`를 보여 준다. 기다리는 사이 커서가 링크 글자 안으로 옮겨져도 결과를 버린다.
  - 호스트 입력란에서 한글 조합을 끝내려고 누른 Esc(`isComposing`, keyCode 229)는 진행 중인 요청을 취소하지 않는다.
- 결과는 커서 자리에 회색(`#9aa29c`) 글자로 표시된다. 이 표시는 편집할 수 없고 클릭도 받지 않는다(`data-review-ui="ghost"`). 화면 낭독기에는 별도 live region으로 추천 문장을 읽어 준다. 후보는 최대 3개다.
  - **Tab**: 추천 전체를 일반 입력처럼 넣는다. 되돌리기(⌘Z)가 되고, 저장 전 변경으로 표시된다.
  - **⌘/Ctrl+→**: 다음 어절 하나(뒤따르는 공백 포함)만 넣고, 나머지는 회색으로 남긴다.
  - **⌥]** / **⌥[**: 다른 후보로 바꾼다. 순번(`추천 1/3`)은 문단 아래 작은 추천 막대에 보인다. 막대에는 `수락`·`한 어절`·`다른 추천`·`다시`·`닫기` 버튼과 키 안내가 있다. 회색 글자는 클릭을 받지 않으므로 마우스·터치로는 이 막대로 수락한다.
  - **⌥\\**: 새로 요청한다. **Esc**: 추천을 닫는다.
  - 추천의 첫 글자와 같은 글자를 치면 그 글자만큼 추천이 줄어든다. 고른 추천의 마지막 글자까지 치면 추천이 끝나며, 그 추천으로 시작하는 더 긴 다른 후보가 이어서 뜨지 않는다. 다른 글자를 치거나 커서를 옮기거나 포커스를 잃으면 추천을 닫는다. 잠금, 본문 교체, 다시 불러오기·저장(프레임 재생성), 서식 적용, 메모 작성, 한글 조합 시작 때도 닫는다.
  - 제안 카드 다시 그리기 때는 닫지 않는다. 다시 그리기는 문단 안을 건드리지 않고 위치 계산도 회색 추천을 건너뛰기 때문이다. 제안이 있는 문단에서 이어 받기를 하면 입력마다 다시 그리기가 일어나므로, 이때 닫으면 추천이 바로 사라진다.
  - 한글은 조합이 시작되면 추천이 닫히므로 이어 받기가 되지 않는다. 라틴 문자·숫자·구두점·공백만 이어 받는다. 모바일 가상 키보드도 조합 입력이라 막대 버튼으로 수락한다.
  - 표시할 때 나눈 텍스트 노드는 닫을 때 다시 합친다. 추천을 보이고 닫기만 해서는 정본 source나 저장 상태가 바뀌지 않는다.
- 추천을 만드는 동안 서버(`POST /api/blog/suggest`)는 파일을 쓰지 않는다. 저장 전 문단 원문과 plain-text 커서 위치를 받아 앞뒤 문장, 이웃 묶음 마크업, 노트의 `## 규칙`, 검토 기준, 제목, 이웃 문단의 사람 메모(명령이 아닌 데이터)를 묶어 워크플로 서버의 `suggest-inline` 동작([워크플로 문서](workflows.md#inline-suggestions-suggest-inline--2026-11-03))을 동기로 호출한다. 마크업 기호·줄바꿈을 지우고, 커서 뒤 문장을 되풀이하는 후보와 중복 후보를 걸러 낸다. 길이는 240자 이하로 자른다. 엔진에 연결하지 못하면 `추천 엔진에 연결하지 못했어요. 워크플로 서버가 실행 중인지 확인해주세요.`를 보여 준다.
- 회색 추천·회전 표시·안내 상자는 리뷰 UI(`data-review-ui`)라서 직렬화·plain-text 매핑·메모 위치 계산에서 빠진다. 서식 적용과 메모 작성 전에도 회색 추천을 먼저 지운다. 받아들인 글자만 정본·저장 본문·미리보기·발행 결과에 남는다.
- 상단 도움말 줄에 Tab 키 사용법을 짧게 덧붙였다.
- 추천은 워크플로 서버의 새 `suggest-inline` 동작을 쓰므로, 이 변경 이전에 띄운 워크플로 서버(기본 4318)는 다시 시작해야 한다. 다시 시작하지 않으면 원문 오류 대신 `실행 중인 워크플로 서버가 이전 버전이에요…` 안내가 보인다. 데스크톱 앱은 이전 버전 서버를 감지해 워크플로 화면에도 같은 안내를 띄운다([내장 서버](workflows.md#desktop-embedded-server--2026-11-03)).
- 끝 공백 처리: 모델이 문장 중간 이어 쓰기 끝에 공백을 붙여 돌려주면(예: `빵을 사서 ` 뒤에 `집에…`) 그 공백을 보존한다. 실제 엔진 확인에서 이 공백이 잘려 `사서집에`가 되는 문제를 발견해 고쳤다.

검증(2026-11-03, 합성 원고만 사용):

- `npm test`는 Homebrew Node 26에서 220/220 통과했다. 여기에는 `inline-suggest`, `workflow-suggest`, `blog-suggest` 단위 테스트가 포함된다.
- `npm run build:web` 후 headless 웹 spec 7개 파일(`canonical-tab-suggest`, `canonical-inline-review`, `canonical-blog`, `canonical-formatting`, `canonical-save-status`, `canonical-sdk`, `markup-layout`)이 12/12 통과했다. 같은 묶음을 `--repeat-each 3`으로 돌려 36/36, `canonical-tab-suggest`만 `--repeat-each 3`으로 돌려 12/12 통과했다.
- 반복 실행에서 테스트 종료 시 편집 서버 `close()`가 끝나지 않는 문제가 있었다(2/12 시간 초과). 페이지가 1.5초마다 review-status를 폴링하면서 keep-alive 연결을 계속 다시 쓰기 때문이었다. `close()`가 진행 중 응답에 `Connection: close`를 붙이고, 유휴 연결을 닫고, 2초 뒤 남은 연결을 강제로 닫도록 고쳤다.

- 스크린샷으로 데스크톱(1440px)과 모바일(390px)의 안내 상자, 회전 표시, 회색 추천을 확인했다. 안내 상자는 대상 바로 아래 제안 카드의 윗부분을 일부 가린다. 포인터는 통과하지만 디자인을 다듬을 여지가 있다.
- 후속 수정(2026-11-03): 리뷰에서 확인된 다섯 가지를 고쳤다. ① 기다리는 동안 포커스가 문단을 떠나도 늦은 응답이 회색 추천을 띄우고 포커스를 되돌리던 문제, ② 링크 글자 안의 커서가 모두 링크 시작 위치로 계산돼 위치 변경을 알아채지 못하던 문제, ③ 호스트 입력란에서 한글 조합을 끝내는 Esc가 요청을 취소하던 문제, ④ 고른 추천을 끝까지 쳤을 때 더 긴 다른 후보가 이어서 뜨던 문제, ⑤ 기다리는 동안 같은 끝 위치로 선택을 만들면 결과가 적용되며 선택이 풀리던 문제다. `canonical-tab-suggest`에 이 다섯 경우를 확인하는 브라우저 테스트 1개를 추가했다. 수정마다 그 수정만 되돌려 실행하면 이 테스트가 실패하는 것도 확인했다. 포커스 확인을 응답 시점과 `focusout` 즉시 취소 두 곳에서 하는데, `focusout` 즉시 취소만 되돌렸을 때는 응답 시점 확인이 같은 결과를 막아서 테스트가 통과했다.
- 후속 수정 뒤 다시 확인한 결과: `typecheck`, `check:architecture`, `audit:public`(567 entries)이 통과했고, `npm test`는 220/220 통과했다(이번 테스트는 웹 spec이라 단위 테스트 수는 그대로다). `npm run build:web` 뒤 같은 웹 spec 7개 파일이 13/13 통과했고, `--repeat-each 3`으로 39/39 통과했다. `npm run build` 뒤 Electron background QA(`markup-editor`, `blog-scroll`)는 4개 통과, 2개 건너뜀으로 이전과 같다. 데스크톱·390px 스크린샷을 다시 찍었다. 실제 엔진 지연 측정은 다시 하지 않았다(아래 수치는 이전 측정이다).
- 실제 Codex(저장된 로그인, 기본 모델, effort low)로 별도 포트의 워크플로 서버를 띄워 `suggest-inline`을 확인했다. 응답이 온 호출은 5.3~12.2초 걸렸다. 같은 시간대에 응답 이벤트 없이 90초 시간 초과로 끝난 호출도 많았다. 같은 시간에 일반 `codex exec`도 90초 동안 응답하지 않아, 백엔드나 계정 쪽 지연으로 판단했다. 커서 뒤에 새 사실이 필요한 위치(문단 끝)에서는 지어내지 않도록 빈 목록을 돌려주는 경우가 많았다.

## 기본 스티커 배치 — 2026-11-03

마크업 정본 편집기의 **스티커** 버튼에서 네 가지 용도를 선택하고 문단·사진 사이에 자리를 놓는다. 실제 네이버 기본 스티커는 이관 시 선택하며, 대시보드는 위치·선택 메모와 자리 표시를 저장한다. 배치 메모 복사, 과도한 사용 안내, 위치 보기·이동·삭제를 지원한다. [사용법과 저장 계약](blog-stickers.md).

## 묶음 삭제·저장 단축키 — 2026-11-03

- **⌘/Ctrl+S**: 본문(iframe) 안이나 바깥 어디서든 정본 저장 버튼과 같은 저장을 실행한다. 변경이 없으면 `저장할 변경이 없어요.`만 표시하고, 입력 오류가 있거나 저장 중이면 실행하지 않는다. IME 조합 중에는 무시한다.
- **묶음 삭제**(markup 원고만): 본문에서 묶음의 글 밖(이름표·사진 등)을 클릭하면 묶음 테두리가 표시되고 Delete/Backspace로 지운다. 글 안에 커서가 있을 때 Backspace는 평소처럼 글자만 지운다. 왼쪽 글의 흐름 항목에 포커스를 두고 Delete를 누르거나 도구줄 **묶음 삭제**를 눌러도 된다. Esc는 묶음 선택을 해제한다.
- 삭제는 화면에서 먼저 숨기고 **저장 전 변경**으로 남는다. **삭제 취소 (n)**은 마지막 삭제부터 되돌린다. 저장하면 `deleteBundles`로 서버에 전달되고 해당 묶음(안의 문단·사진·스티커 포함)이 정본에서 빠진다. 다시 불러오기는 삭제를 버린다.
- 마지막 남은 묶음은 지울 수 없다. 지운 묶음의 앞뒤 묶음은 변경분 검토 대상에 추가된다. 지운 묶음의 기존 리뷰 기록과 사용자 주석 파일은 수정하지 않는다.

검증: headless `canonical-bundle-delete` 2개(프레임/호스트 ⌘S, 글 안 Backspace 보호, 이름표 선택 후 Delete·Backspace, 삭제 취소, 저장 후 정본에서 제거, 글의 흐름 Delete, 마지막 묶음 보호)와 기존 canonical·markup-layout spec, 단위 테스트, 타입·FSD 검사.

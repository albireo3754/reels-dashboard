## Executable markup reviews — 2026-11-01

The editor now owns a persistent-request consumer. Opening the markup editor resumes pending/running request receipts, and the review button submits immediately. The consumer calls the existing loopback workflow service's review-markup endpoint; CodexExecutor reuses saved-login/API selection, read-only sandboxing, streamed jobs and observation. No automatic source edits or publishing occur.

Request IDs are idempotency keys in the workflow job store. Restarting a consumer cannot launch the same request twice; reusing an ID with different input is rejected. Duplicate active requests for the same snapshot/annotations return the existing request. A failed request requires an explicit new review action. Dead-process consumer locks are cleaned up; malformed locks/errors are surfaced instead of silently waiting.

Results must contain exactly the requested bundles. Proposed text and emphasis targets are validated against the original paragraph text, and the model receives an enum of valid paragraph IDs. It distinguishes pending, running, completed, failed, cancelled, interrupted and stale; failed/stale jobs expose a retry action. The old draft-only SDK button stays separate. The workflow server must be running; unavailable engines produce a visible failure and retry button. Review jobs can finish while the editor is closed; results are imported when the editor next opens. ## Tab suggestions — 2026-11-03

Cursor-style keyboard suggestions in the markup editor, in two layers. Neither layer changes the manuscript until the writer explicitly accepts with a key.

> **Superseded in part 2026-11-03:** the hint popover placement, the "caret in paragraph, else nearest after" activation and the card references are replaced by [In-text diff proposals](#in-text-diff-proposals--2026-11-03).

**Layer 1 — Tab over review proposals.** No new review machinery. This layer uses the live inline proposals (`planInlineProposals` items that have `start`/`end` in the current paragraph mapping).
- When the caret is in a paragraph with an active proposal, a hint popover appears under the target range. The active proposal is the one containing the caret, or else the nearest one after it. The popover is `<div data-review-ui="hint" role="status" aria-live="polite">`, clamped to the paper width, and only its buttons take pointer events. It shows the compact diff, `Tab 적용 · Esc 유지 · Shift+Tab 이전` and a `다시 검토` button that re-requests review of that paragraph's bundle through the existing request flow.
- `Tab` with the caret on or next to an applicable proposal sends `proposal-action apply` with the proposal signature. Apply is unchanged: target validation, stale lock and signature check still run. The caret then moves to the next live proposal in document order, resolved from the refreshed `proposals` message and never from a stale offset. With the caret not on a proposal, the first `Tab` only jumps (no apply). `Shift+Tab` jumps to the previous proposal. `Esc` sends `keep` and moves on only when the caret is inside the active proposal's range; a proposal that is merely shown ahead of the caret does not capture `Esc`. The hint is removed from the DOM when inactive; a persistent `data-review-ui="live"` region repeats its text. Frame→host messages `reveal` (scroll only when off-screen) and `review-bundle` were added.
- Blocked proposals (no located range, e.g. link-internal targets) are skipped; their cards keep showing the reason. With nothing ahead or behind, the keys are not intercepted, so there is no focus trap. Keys are ignored while composing (`isComposing`, keyCode 229), while locked, and with modifiers other than Shift.

**Layer 2 — manual ghost-text suggestion.** Never triggered by typing.
- Trigger: toolbar **✦ 추천 받기** (`aria-keyshortcuts="Alt+Backslash"`) or `Alt+\` (`e.code === "Backslash"`) inside the frame. Markup documents only; on legacy documents the button is disabled with an explanatory title.
- The host takes the caret from the frame: paragraph id, plain-text offset (the end of a selection if there is one) and the current unsaved inline source. It then calls `POST /api/blog/suggest` with an `AbortController`. While pending, the button shows a spinner and `추천 중… (Esc 취소)`, and the frame shows `data-review-ui="spinner"` at the caret rect with a `추천을 기다리는 중` status. `Esc` or a new request aborts the pending one.
- A result is discarded if the paragraph source, caret offset, selection (start offset and collapsed state), live focus (`document.activeElement` must still be the paragraph) or document revision changed meanwhile. The notice is `본문이 바뀌어 추천을 버렸어요. 다시 요청해주세요.` An empty result shows `이 위치에 추천할 문장이 없어요.`
  - `selected` and `getSelection()` both survive a blur, so they are not used alone as the focus check. A `focusout` from the requesting paragraph to another element in the frame (`relatedTarget` set) cancels the request at once; a window/app switch (no `relatedTarget`) keeps it. A late answer therefore never pulls focus back into the paragraph.
  - Every caret strictly inside a link label maps to the link's start offset (`offsetOf`), so `caretInfo()` reports `inLink`. A request there is refused with `링크 글자 안에서는 추천할 수 없어요. 링크 앞이나 뒤에 커서를 두고 다시 요청해주세요.`, and a caret moved into a label while waiting makes the result stale.
  - The host's pending-request `Esc` listener ignores `isComposing` / keyCode 229, so ending a Hangul composition in a host field does not cancel the request.
- The ghost is `<span data-review-ui="ghost" contenteditable="false" aria-hidden="true">` with color `#9aa29c` and `pointer-events:none`, inserted at the caret; a live region announces the text. Keys:
  - `Tab` removes the ghost and runs `execCommand('insertText')`, so undo works and the normal `change` flow follows.
  - `Cmd/Ctrl+→` accepts the next word (up to and including the next whitespace).
  - `Alt+]` / `Alt+[` cycle up to three alternatives. The `추천 n/3` indicator lives in a small suggestion bar under the paragraph with `수락`, `한 어절`, `다른 추천`, `다시` and `닫기` buttons, because the ghost itself ignores pointer input (needed for mouse/touch acceptance).
  - `Alt+\` re-requests; `Esc` dismisses.
  - Typing the ghost's first character trims the ghost (type-through); any other character dismisses it. Typing the selected candidate's last character finishes it; a longer candidate that starts with it does not take over.
  - Caret move, blur, lock, replace, save, reload (frame rebuild), formatting, annotation capture and `compositionstart` also dismiss it. A proposals re-render does **not** dismiss it: re-rendering never touches paragraph content and mapping skips the ghost, while type-through in a paragraph with proposals re-renders on every keystroke.
  - Because `compositionstart` dismisses the ghost, Hangul and mobile virtual keyboards cannot type through; they accept via the bar buttons.
  - Text nodes split to place the ghost are re-joined on dismissal, so showing and dismissing a ghost never changes the source or the dirty state.
  - Messages: frame→host `suggest`, `suggest-cancel`, `suggest-done`, `suggest-error`; host→frame `suggest-start`, `suggest-result`, `suggest-cancel`.
  - The ghost is removed before `formatRange` and annotation capture.
- `POST /api/blog/suggest` `{revision, paragraphId, source, offset}` is markup-only (legacy → 400 `이 형식에서는 추천을 지원하지 않아요.`). It validates the paragraph and the offset (400), checks the revision base (409 when expired) and never writes files. It builds `inlineSuggestInput` from the current document with the unsaved paragraph substituted: plain `before`/`after` split at the offset, neighbouring bundles' markup, `## 규칙` rules, configured review guidance and the title. Neighbouring human annotations are included as data. The input is fitted under the proxy body limit. The handler calls workflow `suggest-inline` and runs `cleanSuggestions`, which yields single-line text with markup characters stripped, at most 240 characters, no duplicates, no echo of the text after the caret, spacing fitted to the caret, and at most 3 results. It returns `{requestId, revision, paragraphId, offset, suggestions, elapsedMs}`. If the engine is unreachable it returns 502 `추천 엔진에 연결하지 못했어요. 워크플로 서버가 실행 중인지 확인해주세요.`; if the engine times out it returns 504.
- Leakage guarantees: ghost, spinner and hint are `[data-review-ui]` nodes, which `serialize()`, `plainMap()` and annotation capture skip. Only accepted characters reach the canonical source, saved body, derived preview and publish outputs.
- `cleanSuggestions` keeps a trailing space the model returned before a word that follows the caret (`빵을 사서 ` + `집에…`); the live engine check found it being trimmed into `사서집에`.
- Server shutdown: `startCanonicalEditor().close()` now answers in-flight requests with `Connection: close`, closes idle sockets and force-closes the rest after 2 s. Before this, the page's 1.5 s review-status polling could keep a keep-alive socket in use forever and `close()` never resolved.
- Workflow servers started before this change (default 4318) must be restarted to know `suggest-inline`. The desktop app embeds a current server and reports an older one as stale ([desktop embedded server](workflows.md#desktop-embedded-server--2026-11-03)).

## In-text diff proposals — 2026-11-03

Review cards under paragraphs are gone. Text proposals are drawn as a Cursor-style diff exactly at the target phrase; everything else becomes a small marker. Implementation: `src/app/blog-editor/frame-script.ts` (frame) and `CanonicalBlogEditor.tsx` (host).

**Contract unchanged.** Host→frame `proposals` items and the frame→host `proposal-action` message `{action, id, sig}` are the same, and the host still checks `sig` and applicability (legacy non-markup reviews keep the bundle freshness lock). The only host-side changes: `hasBodyMark` replaces `hasBodyCard` (a proposal in state `changed` is not drawn, and its panel chip reads `본문 변경됨`), and the panel/help text describes inline marks. Frame→host `reveal`, `review-bundle` and host→frame `reveal-proposal` are as before.

**DOM it adds (all `data-review-ui`, all `contenteditable="false"`):**
- Deleted characters: no DOM at all. The CSS Custom Highlight `rv-del` (red strike-through) is painted over Ranges; `rv-target` marks the range of a format proposal; `rv-focus` marks the active proposal.
- Inserted segments: one empty `<span data-review-ui="ins" data-pid data-text>` per segment, drawn by `::after { content: attr(data-text) }` (green text, light green background, underline). Because the text lives in an attribute, `textContent`, `innerText`, `Range.toString()` and `serialize()` never see it. When the diff segments do not map onto the paragraph (for example at a link boundary), the whole target range is struck through and a single `ins` follows it.
- Markers: `<span data-review-ui="marker" data-pid data-label>` with `✦ 서식` (format), `✦ 메모` (note), `⚠ 확인 필요` (blocked, link-partial or `!canApply`) and `✦ 겹친 제안` (text proposal overlapping an earlier inline one). Paragraph-less photo/layout notes sit in a `data-review-ui="note-row"` next to the related photo or the bundle label. A marker never splits an inline diff; it moves to the diff's end.
- Only the first of overlapping text proposals is inline. The others stay markers until the host re-validates after a decision. A proposal whose state is `changed`, or that is not found uniquely at its offsets, draws nothing.
- One popover `<div data-review-ui="hint" role="group">` for the active proposal (caret in or touching it, `Tab`/`Shift+Tab`, click/tap on an `ins`/`marker`, or panel `reveal-proposal`), plus the persistent `data-review-ui="live"` region. The popover is clamped to the paper width, flips above when it would be clipped, never covers the target line, and spans the paper like a sheet when the paper is narrower than 520px. Buttons: `적용` (Tab), `유지` (Esc), `이유`, `다시 검토`. Mouse-down on review controls is prevented so the caret stays in the paragraph.

**What skips review nodes:** `serialize()`, `plainMap()` (hence `boundary`/`offsetOf`/`rangeOf`), annotation capture and `formatRange` (which holds the paragraph's review nodes first). `copy` and `dragstart` inside one paragraph hold that paragraph (review nodes removed, selection kept) and let the browser copy natively so enclosing formatting survives; a multi-paragraph copy clones the selection and strips `[data-review-ui]` before writing `text/plain` and `text/html`. `selectionState()` drops a ghost the selection moved across before reporting the selected text.

**Popover details.** Only buttons and the reason text take pointer events, so clicks elsewhere reach the manuscript under the popover. A marker popover is placed clear of both the marker and the phrase it names (`anchor` range). `Alt+ArrowDown` moves keyboard focus into the popover; `Esc` there returns to the saved caret without a decision. Deferred overlap markers are blocked (never applied from the marker). Markers get a 36px+ tap area via vertical padding/negative margin (line box unchanged).

**Edit safety.** `keydown` of an edit key, `beforeinput`, `compositionstart` and `cut` call `holdParagraph`: the paragraph's `ins`/`marker` nodes are removed at once (caret saved and restored, split text nodes re-joined with `normalize()`), and the paragraph stays undecorated until `scheduleRender` fires after 400 ms idle. While IME composition is active nothing is redrawn; `compositionend` schedules the redraw. A ghost suggestion (layer 2) on the paragraph also keeps its diff off and hides the hint, and while it is visible it owns the keys.

**Keys** (ignored while composing, locked, or with Alt/Ctrl/Cmd): `Tab` on an applicable active proposal sends `proposal-action apply` and then moves to the next proposal once refreshed `proposals` arrive (never a stale offset); `Tab` elsewhere jumps to the next without applying; `Shift+Tab` goes to the previous; `Esc` on a proposal sends `keep` and moves on. With nothing ahead/behind, or `Esc` off a proposal, the event is not intercepted, so there is no focus trap.

**Leakage guarantee.** Nothing in the manuscript changes before an explicit apply. Review UI never reaches the canonical source, saved body, derived preview, publish output or hidden capture windows.

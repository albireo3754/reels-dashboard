# 제작 프로젝트 모델

대시보드의 카드 하나가 하나의 제작 프로젝트다. 주제·진행 상태·문안·원본 자료를 프로젝트에서 관리하고, 영상 편집과 카드뉴스 구성은 프로젝트에 소속된 편집 작업이다. 구성이나 출력 버전이 늘어나도 별도 콘텐츠 카드로 분리하지 않는다.

## 스키마

- [JSON Schema](../schemas/dashboard.schema.json): Dashboard → Project → production의 전체 저장 형식.
- [타입·관계 검증](../src/shared/production-project.ts), [저장 검증](../src/shared/data.ts).
- 생성: `node --import tsx scripts/write-project-schema.ts`. JSON Schema는 필드 구조를 검증하고, 소유권·참조 무결성은 저장 시 `validateProductionLinks`가 검증한다.

| 단위 | 키와 소유 관계 | 저장 내용 |
| --- | --- | --- |
| Dashboard | 프로젝트 ID가 유일한 projects 배열 | schemaVersion, updatedAt |
| Project | 콘텐츠 수명 동안 유지하는 id | 제목·진행·날짜·문안/자료 링크·공유 상태 |
| 편집 구성 | (kind, id), 한 프로젝트에만 소속 | video 또는 card-news. 기존 편집 파일을 참조 |
| 출력 이력 | UUID, 편집 구성과 연결 자료 참조 | path, role, recordedAt |
| 병합된 카드 | mergedIds, 다른 카드/별칭과 중복 금지 | 이전 ID 재생성 방지와 내보내기 소유자 해석 |
| outbound | 프로젝트에 고정한 iCloud 경로 하나 | directory, generation, files(이름·역할·크기·해시), updatedAt, 로컬 receiptPath |

`production`은 `{schemaVersion:1, edits:[], exports:[], mergedIds:[]}`다. 기존 dashboard schemaVersion 1에 선택 필드로 추가한다. 기존 기록을 추측해서 일괄 합치거나 편집 구성 ID를 바꾸지 않는다. 실제 연결·병합·내보내기 때 모델이 저장된다. 독립적으로 시작한 편집은 처음에는 자기 ID의 카드를 가지며, 사용자가 대표 프로젝트에 연결/합친 뒤 모든 후속 출력이 그곳으로 들어간다.

`resources`는 현재 자료 목록, `exports`는 어떤 편집에서 생성된 출력인지 추적하는 이력이다. 동일 경로·역할·편집 조합은 중복 기록하지 않는다. `recordedAt`은 이력 등록 시각이며 과거 파일의 실제 생성/게시 시각을 뜻하지 않는다. 기존 수동 연결 자료는 편집 구성을 추측해 출력 이력으로 바꾸지 않는다. 이전 독립 편집 카드와 저장된 구성 ID가 정확히 같은 경우에만 병합 때 이력을 연결한다.

영상/표지 출력 및 카드뉴스 MP4 출력은 편집 소유자를 조회해 같은 프로젝트에 자료·이력을 추가한다. 대표 제목·날짜·공유 설정을 유지하고, 이미 게시한 프로젝트는 재출력으로 미게시 상태가 되지 않는다. 편집 설정·개인 미디어는 원래 파일에 남는다. 공유 snapshot에는 편집 ID·별칭·출력 경로를 포함하지 않는다.

## 통합 프로젝트 모델 — 2026-11-10 계획

### 프로젝트별 outbound — 2026-11-11 구현

`Project.outbound`는 실제 구현된 전달 계약이다. 전달마다 폴더를 바꾸지 않고
프로젝트에 한 번 저장한 경로와 고정 파일명을 갱신한다. 교체 전 파일·영수증은
앱 로컬 이력에 보관하며 iCloud에는 현재 전달 파일만 남긴다. 다른 프로젝트와
겹치는 경로는 거부한다. 기존 콘텐츠 upsert와 앱 재시작에도 경로를 유지하고,
공개 snapshot에는 넣지 않는다. 관리 대상이 아닌 파일은 건드리지 않는다.
직접 렌더한 출력 이력이 교체될 경로를 참조하면 이전 파일의 로컬 보관 경로로
참조를 옮겨 과거 편집과 바뀐 파일을 혼동하지 않게 한다.

서로 다른 outbound를 가진 프로젝트의 병합은 거부한다. 한쪽에만 있으면
병합 결과에 이어받는다. [MCP 사용법](mcp-usage.md#icloud-delivery-api--2026-11-11).

### 통합 산출물 모델 계획

사용자 결정: 릴스 영상·카드뉴스·블로그(이후 네이버클립 포함)를 모두 **프로젝트** 하나로 정리한다. 같은 소재라면 데이터 소스는 같다. 다만 산출물마다 표현하려는 내용, 쓰는 데이터의 종류, 참고하는 레퍼런스가 다르다. 그래서 공통 소스는 프로젝트에 두고, 다른 부분은 산출물에 둔다. 아래는 아직 구현 전인 설계 기준이다.

| 층 | 무엇을 담나 | 지금 있는 것 |
| --- | --- | --- |
| 프로젝트(소재) | 한 번의 방문·촬영 단위. 제목·날짜·진행, 원본 자료(Photos·로컬 폴더), 이미지·영상 분석 결과, 장소·메뉴·촬영 맥락, 경험 질문 답변 | `Project`, `resources`, 미디어 분석·증거 루프 결과, 경험 질문 폼 |
| 산출물(output) | 채널별 결과물. `kind`(reel-video · card-news · blog · naver-clip …)와 그 kind 전용 편집 데이터, 원본 중 고른 부분, 레퍼런스, 출력·게시 상태 | `production.edits`(video·card-news), 콘텐츠 카드에 연결된 blog-markup 원고(2026-11-12부터 별도 등록 없음) |
| 출력 이력 | 산출물에서 나온 파일과 게시 URL | `production.exports`(영상·카드뉴스만) |

산출물마다 달라지는 것:

- **표현**: 릴스는 컷·자막·장소 안내·표지가 중심이다. 카드뉴스는 카드 순서와 문구 표가, 블로그는 문단·사진 묶음·콜라주·스티커가 중심이다.
- **데이터 선택**: 같은 원본에서 고르는 범위와 단위가 다르다. 릴스는 영상 구간 몇 개를 쓰고, 블로그는 사진 수십 장과 그 비율·묶음을 쓴다. 선택 결과는 산출물에 두고, 원본과 분석 결과는 프로젝트에서 공유한다.
- **레퍼런스**: 기본적으로 산출물에 붙인다. 네이버 블로그 추출본은 블로그 산출물에, 릴스 레퍼런스는 릴스 산출물에 붙인다. 여러 산출물이 같이 쓸 근거(장소 사실, 메뉴 근거)만 프로젝트에 둔다.
- **문안·리뷰 규칙**: 캡션·댓글과 블로그 본문은 정본 위치가 다르고(Obsidian 콘텐츠 문서 / 블로그 정본), 말투 리뷰 어댑터도 다르다. 프로젝트는 링크만 갖고 문안을 복제하지 않는다.

정리 원칙:

- 프로젝트 ID가 모든 화면·MCP·herdr 세션의 공통 키다. 세션 맥락은 `projectId` + 지금 연 산출물(`kind`, `id`)로 넘긴다.
- 블로그 등록은 `projectId`로 기존 프로젝트에 연결한다. 이름이나 날짜가 비슷하다는 이유로 자동 연결하지 않고, 기존 병합 규칙처럼 사용자가 명시적으로 연결한다. 연결 전 블로그는 자기 ID로 프로젝트를 갖는다.
- `editRefSchema.kind`에 `blog`를 더할지, 산출물 목록을 새로 둘지는 구현 설계 때 정한다. 기존 `production` 저장 형식과 MCP(`reels_link_project_edit`, `reels_merge_projects`)는 호환을 유지한다.
- 블로그 출력(네이버 이관 결과, 게시 URL)도 출력 이력에 넣는다.

### 채널별 게시 상태 — 2026-11-12 구현

통합 산출물 모델 중 **게시 상태**만 먼저 구현했다. `Project.publications`는 채널(`instagram`·`naver-clip`·`blog`)당 한 항목이며 `status`(`planned`·`published`), `url`, `publishedAt`(게시 완료일 때만)을 가진다. 항목이 없는 채널은 그 프로젝트의 목표가 아니다. [타입·검증](../src/shared/publications.ts).

- 완료 기준: 채널마다 따로 본다. `reels_set_publication`으로 목표 채널이 전부 `published`가 되면 프로젝트 `stage`를 `published`로 올린다. 이후 채널을 더하거나 되돌려도 `stage`를 내리지 않는다. 남은 채널을 `planned`로 먼저 등록하지 않으면 채널 하나만으로 완료가 된다.
- 보드의 채널 필터는 그 채널 항목이 있는 프로젝트만 보여주고, **진행 중**은 그 채널이 아직 게시 전인 것, **게시 완료**는 그 채널이 게시된 것으로 판정한다. 다른 진행 단계를 고르면 그 채널이 게시 전이면서 해당 단계인 프로젝트만 남는다.
- `publicURL`은 채널 항목이 없는 기존 프로젝트의 링크로 계속 쓴다. 채널 항목이 있으면 카드에는 채널 칩의 링크만 보인다. 기존 값을 채널 항목으로 자동 변환하지 않는다. 어느 채널 링크인지 추측하지 않기 위해서다.
- 이 필드는 기록이다. 게시·업로드·게시 여부 확인을 하지 않으며 공유 snapshot에 포함하지 않는다. 산출물(kind)별 편집 데이터·레퍼런스 분리는 여전히 계획 단계다.

## 앱 사용법

### 프로젝트 터미널 — 2026-11-12

데스크톱 보드 카드의 **프로젝트 터미널 → Codex 터미널 열기**로 선택한 콘텐츠 프로젝트를 대상으로 새 세션을 시작한다. 작업 요청을 입력하면 프로젝트 ID·제목과 함께 전달하며, 비워두면 읽기 전용 확인 후 후속 요청을 기다리도록 전달한다. 전달할 프롬프트는 대화상자에서 펼쳐 확인할 수 있다. 시작 실패 시 입력을 보존하고, 성공하면 하단 터미널을 펼쳐 새 탭을 선택한다.

**다음 작업 가이드 넣기**는 현재 6개 단계(아이디어·촬영 완료·촬영본 선택·편집 중·검토 대기·게시 완료), 기록된 다음 할 일, 채널별 게시 상태를 반영한 작업 순서와 확인 기준을 요청 뒤에 추가한다. 입력한 요청을 보존하고 같은 가이드의 중복 추가와 8,000자 초과를 막는다. 버튼 자체는 세션을 시작하지 않으며 내용을 수정한 뒤 **Codex 터미널 열기**로 전달한다. 가이드는 현재 보드 정보로 생성한다. 연결된 워크플로의 실제 대기 작업·완료 기준은 세션에서 조회해 우선 적용하도록 안내하며, 앱이 워크플로 실행 상태를 조회·전환하거나 자동으로 게시하지 않는다.

후속 빌드·실행 검증: 타입·FSD·웹/desktop 빌드와 관련 단위 24개, 새 패키지의 background Electron 2개 통과. 기존 요청 보존·가이드 전달·중복 추가 방지·실패 시 보존·새 세션 선택을 확인했다. 기존 native helper/runtime을 포함해 별도 패키징한 후 `release/mac-arm64/Reels Dashboard.app`에 반영했고, 이전 앱은 `release/before-project-terminal-guide-20261112/Reels Dashboard.app`에 보존했다. 같은 사용자 프로필로 `REELS_DEV_MODE=1`을 지정해 실행하고 실제 대시보드의 프로젝트 터미널 버튼을 확인했다. 실제 모델 작업은 제출하지 않았다.

- 앱 개발용 `workPrompt`와 별도의 콘텐츠 작업 프롬프트를 사용한다. 보드 ID로 `reels_get_content`를 먼저 조회하고, 연결된 편집 구성 ID와 콘텐츠 정본을 확인하도록 안내한다. 개인 경로·자료 본문은 초기 요청에 복제하지 않는다.
- 터미널이 꺼져 있어도 버튼과 설정 안내가 보인다. **설정 → 터미널 사용** 후 재실행해야 하며, 공유 웹에는 이 버튼과 셸 bridge를 노출하지 않는다.
- 새 세션은 Codex의 기존 승인 모드(`permission: ask`)로 시작한다. 기존 대화를 자동 재개하거나 프로젝트별 세션을 영구 연결하지 않는다. 작업 폴더는 연결한 Dashboard 앱 소스를 유지하며 프로젝트 폴더로 자동 이동하지 않는다. 프로젝트의 최신 저장 자료는 MCP/CLI로 확인한다. Codex 설치·로그인과 앱 소스 연결은 기존 터미널 요구사항을 따른다.
- 검증: 타입·FSD·웹/desktop 빌드, 관련 단위 24개, Electron background QA 프로젝트 2개·블로그 2개, 웹 보드 3개 통과. 실제 PTY 입출력까지 확인했으며 에이전트 명령은 QA 셸로 대체했다. 모델의 실제 콘텐츠 수정·운영 데이터 변경·설치 앱 교체는 실행하지 않았다.
- 추가 실행한 기존 `workbench-request.spec.ts` 1개는 기대값에 `permission: ask`가 없어 실패했다. HEAD의 `DevWorkspace.tsx`도 이미 permission을 보내므로 이번 변경과 무관한 기존 기대값 불일치이며 수정하지 않았다.

### 프로젝트로 묶기

콘텐츠 카드의 **수정 → 프로젝트로 묶기**에서:

1. 저장된 편집 구성을 선택해 연결한다. 다른 카드에 속한 구성은 그 카드를 먼저 합친다.
2. 중복 카드에서는 **이 카드를 합칠 프로젝트**에 대표 카드를 선택한다.
3. 표시된 병합 내용을 확인하고 **선택한 프로젝트로 합치기**를 누른다.

제목 등 수정 중인 내용은 먼저 저장해야 한다. 대표 프로젝트의 제목·날짜·진행·공유 상태를 유지하고 자료·편집 연결·출력 이력·메모를 합친다. 다른 게시 링크가 있으면 자동으로 버리지 않고 병합을 거절한다. 원본 미디어·편집 파일은 삭제하지 않는다.

병합은 dashboard revision 확인 후 한 번의 원자적 저장으로 수행한다. 성공 전 전체 기존 dashboard를 앱 user-data의 `documents/project-merge-backup-*.json`에 보관한다. 데이터 한도를 초과하거나 잘못된 참조가 있으면 저장하지 않는다. 자동 되돌리기 UI는 없으며 복구는 앱을 종료한 뒤 백업을 검토해 적용한다. 이후 변경이 생겼다면 전체 백업으로 덮어쓰지 말고 필요한 프로젝트만 복구해야 한다.

## MCP

- `reels_list_project_edits`: 저장된 편집과 대표 프로젝트 조회.
- `reels_link_project_edit`: projectId + edit(kind/id) + expectedUpdatedAt.
- `reels_merge_projects`: targetId + sourceIds + expectedUpdatedAt. 결과에 dashboard와 backupPath 포함.

프로젝트 병합은 콘텐츠 조직 변경이다. 게시·업로드·원본 이동/삭제가 아니다. 예전 카드 ID로 upsert하면 대표 ID를 사용하라는 오류를 반환한다. 이름·파일명 유사성만으로 자동 병합하지 않는다.

## 편집기 단독 카드 정리 — 2026-11-12

영상 편집기는 프로젝트 맥락 없이 영상을 열면 파일명을 제목으로 한 카드를 만든다(`upsertExportedProject`). 앱은 이 카드를 자동으로 합치지 않는다. 정리는 수동으로 시작한다.

- **버튼:** 개발 모드 대시보드 보드 도구줄의 **프로젝트 정리**. 기본 코딩 도구로 새 터미널 세션을 열고 [reels-project-tidy 스킬](../skills/reels-project-tidy/SKILL.md)을 실행하라는 요청(`projectTidyTask`)을 넣는다. 승인 없이 실행(YOLO) 여부는 마지막 선택(`savedAgentPermission`)을 따른다.
- **스캔:** `reels_scan_orphan_edits`(CLI `reels scan-orphan-edits`, 읽기 전용). 대상 카드는 자기 ID의 video 편집 1개만 가지고, 제목이 첫 footage 파일명 그대로이며, 게시 전인 카드다. 후보 프로젝트마다 다음 두 신호를 표시한다. 두 신호를 모두 가진 후보가 정확히 하나일 때만 `suggestedTargetId`를 준다.
  - `folderMatch`: footage가 그 프로젝트의 folder 자료 안이나 Naver Clip 아래 같은 촬영 폴더에 있다.
  - `documentMention`: 연결된 `.md`·`.txt`·`.json` 문서(2 MiB 이하)에 footage 파일명이 나온다.
- **병합:** 스킬이 카드별 근거를 병렬로 확인한 뒤 `reels_merge_projects`로 하나씩 합친다. 병합마다 위의 전체 백업이 남는다.

같은 촬영 폴더의 원본으로 새 릴스를 만드는 경우가 있다. 그래서 촬영 위치만으로는 제안하지 않는다. 판정 함수는 `src/features/content-library/api/orphan-edits.ts`, 테스트는 `tests/unit/orphan-edits.test.ts`다.


## 검증 — 2026-10-31

단위 검사 전체, 타입·FSD·빌드 통과. 프로젝트 관계 단위4개는 병합 백업·자료 보존·충돌·재시작·이전 ID 재생성 방지·소유권과 출력 참조를 검증한다. 개발/패키징 Electron 각각3개에서 UI 병합·재시작, 카드뉴스 병합 후 두 번째 실제 MP4 출력, 영상/표지 실제 출력의 대표 프로젝트 연결을 확인했다. 실제 사용자 라이브러리에서도 승인된 중복 콘텐츠 한 쌍만 병합하고 저장된 편집3개를 연결했으며 다른 프로젝트 불변을 확인했다. 새 앱 `release/production-projects/mac-arm64/Reels Dashboard.app`을 실행했다. 과거 수동 등록 자료 전체의 출력 생성 이력을 추정 복원하지는 않는다.
